# Part 1: Elevator Pitches

## The 30-second version

"HydraCache is a distributed in-memory cache I built from scratch in Go — think
a small, from-first-principles version of Redis, but designed as a distributed
systems project rather than a single-node key-value store. It speaks the real
Redis wire protocol, so `redis-cli` and Go's `go-redis` client work against it
unmodified. Under the hood it implements consistent hashing to shard data
across nodes, asynchronous replication with a per-shard leader, a phi-accrual
failure detector and gossip protocol to track cluster health, a simplified
Raft-style election for cluster coordination, and a write-ahead log for crash
recovery. I didn't copy Redis's source or use an existing consensus library —
every piece is something I designed, implemented, and load-tested myself."

## The 2-minute version

Say the 30-second version, then add:

"The reason I built it this way instead of a tutorial-style single-file cache
is that I wanted to actually grapple with the hard problems a production cache
has to solve: what happens when a node dies mid-write, how do you avoid losing
data on a crash, how do you know a node is *actually* dead versus just slow,
and how do you route a key to the right shard without every client needing to
know your whole topology.

Concretely: keys are placed on a consistent-hash ring with 150 virtual nodes
per physical node, so adding or removing a node only reshuffles a small
fraction of keys instead of the whole keyspace. Each shard has a primary and
some replicas; writes go to a write-ahead log *before* they touch the in-memory
map, so a crash between those two steps loses nothing. Node health is tracked
with a phi-accrual detector — not a fixed heartbeat timeout — so it adapts to
real network jitter instead of firing false positives on a slow network. And
every replicated write carries a topology epoch, so if a replica's view of
'who is the primary' goes stale after a rebalance, it rejects the write instead
of silently corrupting its state.

I also went back afterward and did a full audit of my own claims: I have a
file called COMMANDS.md that says exactly what's implemented, partial, or
missing, generated by reading the dispatch code, not from memory. That's
something I'd do on a real production system too — I'd rather under-claim and
be right than over-claim and get caught by an SRE at 3am."

## The 10-minute version (walk through it live)

Structure it as a narrated tour, in this order — it mirrors how a request
actually flows through the system, which is the most natural way to explain
any distributed system:

1. **Entry point.** A client opens a TCP connection. The server accepts it
   (or refuses it if `MaxConns` is already reached — that limit is enforced
   *before* `Accept()`, not after, so excess connections never even consume a
   file descriptor/goroutine). If TLS is configured, the handshake happens
   here. See 4.2.
2. **Protocol.** The client sends bytes in RESP (`*2\r\n$3\r\nGET\r\n$3\r\nfoo\r\n`).
   A parser reads that into a `Command{Name, Args}` struct, rejecting
   malformed or oversized input *before* allocating memory for it — this is a
   real security property, not decoration, because a naive parser that reads
   an attacker-supplied length and does `make([]byte, length)` before
   validating it is a memory-exhaustion / crash vector reachable by anyone
   who can open a TCP connection, before they've even authenticated. See 4.1.
3. **Auth gate.** If ACLs are configured, the command is checked against the
   connection's authenticated user and the key pattern they're allowed to
   touch. AUTH and HELLO are the only commands reachable before
   authentication — otherwise no one could ever log in. See 4.10.
4. **Dispatch.** The command handler looks at the command name and routes to
   one of ~20 handler functions (`handleSet`, `handleGet`, ...).
5. **Durability.** For a write like `SET`, the write-ahead log is appended
   *before* the in-memory map is mutated. If the process crashes between
   those two lines, replaying the WAL on restart reproduces the write; if it
   crashes before the WAL write completes, the write never happened at all —
   there is no window where it's "half done." See 4.9.
6. **Routing.** The handler asks the consistent-hash ring "who is the primary
   for this key?" If this node isn't the primary, the write still happens
   locally (a known, documented limitation — see Part 7) but isn't
   replicated by this path. If it *is* the primary, the write is appended to
   a replication stream and fanned out to replicas, tagged with the current
   topology epoch. See 4.4 and 4.5.
7. **Cluster health, running the whole time in the background, independent
   of any client request:** every node gossips its membership view to random
   peers (SWIM-style, with incarnation numbers so a wrongly-suspected node
   can refute the rumor), tracks every peer's heartbeat arrival times to
   compute a phi score, and if a node's phi crosses a threshold and stays
   there past a timeout, it's marked dead and a promotion sequence runs.
   Separately, a lightweight Raft-style election decides which node holds
   "cluster coordinator" status — deliberately *not* the same thing as
   "who owns this shard," because HydraCache shards by consistent hashing,
   not single-leader-owns-everything. See 4.6, 4.7, 4.8.
8. **Observability.** A metrics collector counts requests, hits, misses, and
   now (as of this session) real per-command latency histograms, exposed
   both as JSON (`/api/stats`) and a real Prometheus histogram (`/metrics`).
   A React dashboard polls that JSON every 2–3 seconds. See 4.11, 4.13.

Then, if they want to go deeper on any one box, you drop into that subsystem's
section in Part 4.

# Part 2: The Project Story

**Why does this project exist?** Most "build your own Redis" tutorials stop at
a single-node hash map with a TCP server bolted on. That teaches you sockets
and a protocol parser, but none of the actual hard problems that make
distributed caches (Redis Cluster, Memcached with consistent-hash clients,
DynamoDB, Cassandra) interesting systems: partial failure, network partitions,
replica divergence, and the fact that "the server crashed" is a normal
operating condition you have to design for, not an edge case.

**What was the design goal?** Build every core distributed-systems primitive
from first principles — no copying Redis's source, no pulling in an existing
Raft or gossip library — specifically so that every mechanism in the system is
one you can personally explain, including its failure modes.

**What's the timeline of how it was built, roughly?**
1. Single-node cache engine with TTL and LRU/LFU eviction, RESP protocol,
   TCP server.
2. Consistent hashing with virtual nodes, so multiple nodes can exist at all.
3. Async replication with lag tracking and a promotion mechanism.
4. Phi-accrual failure detection, because a fixed heartbeat timeout gives you
   constant false positives on any real network.
5. A simplified Raft leader election (term persistence, pre-vote, quorum,
   lease-based stepdown).
6. Self-healing: wiring the failure detector's "node is dead" signal into an
   actual promotion of a replica.
7. Write-ahead log persistence and crash recovery, with CRC-validated entries
   and periodic snapshots so the log doesn't grow forever.
8. Observability: Prometheus metrics, a real-time React dashboard.
9. A full audit pass, done adversarially against my own code: going through
   every README/doc claim and checking it against what the dispatch code
   actually does, then fixing the gaps that audit found (dead code that
   claimed to do something but was never called, a config option that
   silently did nothing, a crash bug reachable by any unauthenticated
   connection, a documented CLUSTER subcommand that fell through to "unknown
   command"). Sections 4.1–4.15 each mention what that audit found in their
   subsystem, because "I found and fixed a real bug in my own project" is
   some of the strongest interview material you have — it proves you can
   read your own code critically, not just write it.
10. Hardening: AUTH/ACL, TLS/mTLS, connection limits, protocol-level crash
    hardening, structured logging, graceful shutdown, real
    protocol-compatibility testing against an actual `go-redis` client (not
    just my own hand-rolled test client).
11. A reference application (a small product-catalog API using HydraCache as
    a cache-aside layer over Postgres, with a live "kill a node" control) —
    built to prove the cache-aside pattern works end-to-end against a real
    client library, not just against my own internal tests.
12. Dashboard honesty pass: found and removed several dashboard elements that
    displayed fabricated data (a permanently-static "latency histogram" that
    never reflected real traffic, per-node CPU/memory fields that were wired
    into the JSON API but never actually populated by any code path) and
    replaced them with either real data or an honest "not available" label.

**If asked "what would you do next?"** — see Part 7's limitations list, and
frame your answer as: "the two things I'd prioritize are implementing the
Redis Cluster wire protocol so a real Redis Cluster client can route directly
to shards instead of hitting one fixed node, and extending the gossip payload
to actually carry per-node load/memory data, since right now those fields
exist in the JSON schema but the gossip protocol itself never transmits them —
that's a real gap I found and documented rather than silently leaving broken."

# Part 3: Architecture at a Glance

Look at the diagram in `docs/diagrams/hydracache-architecture.html` (open it
in a browser) while reading this section — it's a to-scale visual of exactly
this.

**One node, from the outside in:**

```
Client (redis-cli / go-redis / hc CLI)
   │  RESP over TCP, optionally TLS, optionally AUTH
   ▼
TCP / RESP Listener  (internal/network.Server)
   │  parsed Command{Name, Args}
   ▼
Command Handler  (internal/network.Handler)
   ├──► In-Memory Cache  (internal/cache)         — the actual GET/SET/DEL
   ├──► WAL + Snapshots  (internal/persistence)   — durability, written first
   ├──► Consistent Hash Ring  (internal/hashring) — "who owns this key?"
   ├──► Replication Stream  (internal/replication)→ Peer HydraCache nodes
   └──► Cluster Coordination                      → Peer HydraCache nodes
        (internal/cluster + internal/election + internal/heartbeat)
```

**Separately, always running, independent of any client request:**
- Gossip exchanges membership state with peers.
- The phi-accrual detector watches heartbeat timing per peer.
- The election loop runs its own timers for votes/heartbeats/lease renewal.

**Separately, observability, pulled by external tools (never pushed):**
- `internal/metrics` aggregates counters + a real latency histogram.
- `/metrics` (Prometheus format) is scraped by Prometheus/Grafana.
- `/api/cluster` and `/api/stats` (JSON) are polled by the React dashboard.

**The trust boundary that matters most:** everything inside one node's
process shares memory directly — no network hop, no serialization. The
*only* way anything gets in from outside that process is (a) the RESP
listener's AUTH/TLS gate, or (b) the metrics HTTP mux (which today has no
auth at all — a real, worth-naming-if-asked limitation). A peer node is a
*separate OS process*; the only thing crossing that boundary is network
traffic (gossip, heartbeats, election RPCs, replication), and those RPCs are
deliberately exempt from the client-facing ACL, because a peer node never
calls `AUTH` — that's not a security hole, it's `internal/network/handler.go`'s
`isInterNodeCommand` function drawing the line correctly between "a client
authenticating as a user" and "a peer proving it's part of the cluster"
(the latter is TLS's job, not implemented as mutual-auth-per-RPC here — see
Part 7).

## 4.1 RESP Protocol

**What.** RESP (REdis Serialization Protocol) is the text-based wire format
Redis and Redis-compatible clients speak. HydraCache implements **RESP2**
only — not RESP3 (see Part 6 for why that's a deliberate choice, not an
oversight).

**Why a real protocol instead of my own?** Because the entire point of
building a "Redis-like" cache is that existing tools (redis-cli, every
language's Redis client library) work against it without modification. If I'd
invented my own wire format, I'd have proven nothing about compatibility.

**The wire format, concretely.** Every message is either:
- A **Simple String**: `+OK\r\n`
- An **Error**: `-ERR message\r\n`
- An **Integer**: `:1\r\n`
- A **Bulk String** (the actual payload type for values): `$5\r\nhello\r\n`
  (the `5` is the byte length, so binary-safe data with embedded `\r\n` is
  fine — length-prefixed, not delimiter-terminated)
- A **Null bulk string**: `$-1\r\n` (RESP2's "nil" — this is what a cache miss
  returns, and what `go-redis` turns into the `redis.Nil` sentinel error)
- An **Array**: `*3\r\n` followed by 3 more RESP values — this is how a client
  actually sends a command: `SET foo bar` is `*3\r\n$3\r\nSET\r\n$3\r\nfoo\r\n$3\r\nbar\r\n`

**Code walkthrough.** `internal/protocol/parser.go` has `NewParserWithLimits(r,
maxBulkLen, maxArrayLen)`. It reads the array header, then reads each bulk
string header, validating the declared length **before** allocating a buffer
for it. `internal/protocol/encoder.go` has the inverse: `WriteSimpleString`,
`WriteError`, `WriteInteger`, `WriteBulkString`, `WriteArray`.

**The security bug this session found and fixed (this is a great interview
story — a real, non-hypothetical crash bug):**
The parser used to do something like `make([]byte, declaredLength+2)` where
`declaredLength` came straight off the wire as a signed integer, with no
validation. If an attacker sent `$-5\r\n` (a negative bulk length — not a
valid RESP null, which is specifically `$-1\r\n`, but any other negative
number), `make([]byte, -5+2)` panics in Go — an unrecoverable runtime panic,
not a catchable error. Because parsing happens *before* the AUTH check, this
was reachable by any TCP connection, authenticated or not — a one-packet
denial-of-service against the whole process. The fix: `NewParserWithLimits`
explicitly rejects negative and over-maximum lengths before doing any
allocation at all, and a `recover()` was added around the per-connection
handling loop as defense-in-depth so a similar bug anywhere else in the
dispatch path drops just that one connection instead of taking down the
process.

**Concurrency.** The parser and encoder are not concurrency primitives
themselves — each TCP connection gets its own goroutine with its own parser
and encoder instance, so there's no shared mutable state to protect *within*
this subsystem. (Compare this to the cache engine in 4.3, which *is* shared
across every connection and does need locking.)

**What tests prove.** `internal/protocol/parser_test.go` proves: negative bulk
length is rejected, not panicked on; an over-maximum length (e.g., claiming a
2GB bulk string) is rejected *before* any allocation happens (proven by not
timing out / OOMing the test); a valid, well-formed command still parses
correctly. `internal/network/limits_test.go` has
`TestServer_MalformedNegativeBulkLengthDoesNotCrashServer`, which sends the
literal malformed packet over a real TCP connection and then proves the
server is still alive by opening a *second*, fresh connection and using it
successfully.

### Q&A: RESP Protocol

**Q: Why RESP2 instead of RESP3?**
A: RESP3 adds new wire types (real booleans, doubles, maps, sets, a distinct
null token) that RESP2 encodes differently (RESP2 has no boolean type at
all, encodes null as `$-1\r\n` instead of `_\r\n`, etc.). Implementing RESP3
"partially" — supporting the negotiation but not the actual new wire types —
would mean a client that successfully negotiates RESP3 then receives
RESP2-shaped replies it wasn't expecting, which is a worse compatibility
story than honestly refusing RESP3 and staying RESP2 throughout. I did
implement the *negotiation* (`HELLO`) so that clients probing for RESP3
degrade gracefully instead of erroring confusingly — `HELLO 3` gets an
honest `NOPROTO unsupported protocol version` (the same error real Redis
uses for a version it doesn't support), and libraries like `go-redis` (whose
default is to request RESP3) already have documented fallback logic for
exactly this response, so they still work, just over RESP2.

**Q: What happens if a client sends a command with the wrong number of
arguments?**
A: `protocol.ValidateCommand` checks the command name against a registry
(`internal/protocol/commands.go`) that records min/max argument counts per
command, and returns `ERR wrong number of arguments for 'get' command` —
matching real Redis's exact error convention (lowercase command name,
`ERR` prefix) so client libraries that pattern-match on that prefix behave
correctly.

**Q: Why validate the bulk-string length before allocating, rather than just
wrapping the allocation in a recover()?**
A: Because `recover()` only catches the panic *after* the damage (or in this
case, the OOM risk) is already underway — a `make([]byte, 2_000_000_000)`
call can exhaust available memory before it ever panics, and even if it
panics cleanly, you've now dropped a connection reactively instead of
rejecting bad input proactively. Validating first means the bad request
never gets a chance to hurt anything. The `recover()` in the connection
handler is defense-in-depth for bugs *I haven't found yet* — it's not a
substitute for validating known-bad input at the boundary.

## 4.2 TCP Network Layer

**What.** `internal/network/server.go` — accepts TCP connections, optionally
wraps them in TLS, enforces a maximum concurrent connection count, applies
per-operation read/write timeouts, and does bounded graceful shutdown.

**Why a semaphore for connection limits, and why does it matter that it's
acquired *before* `Accept()`?**
A semaphore here is just a buffered channel used as a counting lock: a slot is
taken with `s.sem <- struct{}{}` and released with `<-s.sem`. The critical
design point — and a real bug this session found and fixed — is *where* that
slot is acquired. The original code called `Accept()` unconditionally for
every incoming connection and only checked the semaphore *inside*
`handleConnection`, after the connection was already accepted. That means an
attacker (or just organic overload) could keep the kernel handing out
accepted sockets — each one consuming a file descriptor and forcing a
goroutine spawn — far beyond the configured `MaxConns`, because the limit was
only enforced *after* the expensive part had already happened. The fix moved
the semaphore acquisition into `acceptLoop`, *before* calling `Accept()`, so
excess connections are never even given an fd or a goroutine — proven by
`TestServer_MaxConnsThrottlesAcceptance`, which shows the TCP handshake
itself succeeding (the kernel's own backlog accepts it) while the server
doesn't actually *serve* the connection until a slot frees up.

**TLS.** `internal/network/tls.go` builds a `*tls.Config` from cert/key/CA
file paths (`BuildServerTLSConfig`, `BuildClientTLSConfig`) and supports
mutual TLS (`RequireClientCert`). Outbound connections (a node dialing a
peer, or a client dialing the server) go through a single process-wide
`atomic.Pointer[tls.Config]` set via `SetClientTLSConfig` — modeled directly
on how Go's own `http.DefaultTransport` handles a shared, swappable
configuration for every outbound dial in the process, rather than threading a
TLS config through every single call site.

**Graceful shutdown.** `Shutdown()` calls `ShutdownWithTimeout(drainTimeout)`
— it stops accepting new connections, waits (bounded by `drainTimeout`, a
5-second constant) for in-flight connections to finish on their own, and if
that timeout fires, force-closes whatever's left via `CloseAllConnections()`.
Why bounded? Because an unbounded `wg.Wait()` means a single client sitting
idle in a slow read (up to its full configured `ReadTimeout`, which could be
minutes) blocks the *entire process* from shutting down — completely
defeating the purpose of a graceful-shutdown mechanism, which exists so a
deploy or restart doesn't hang indefinitely.

**Structured logging.** Every accepted connection gets a monotonically
increasing `conn_id` (an `atomic.Uint64`), and every log line for that
connection's lifetime is tagged with it via `logger.With("conn_id",
connID, ...)` — so an operator grepping logs can isolate one client's entire
command sequence out of an otherwise interleaved stream from hundreds of
concurrent connections. This is also exactly the value `CLIENT ID` returns to
the client itself.

**Concurrency model.** One goroutine per accepted connection
(`go s.handleConnection(ctx, conn)`), reading commands in a loop until EOF, an
error, or a shutdown signal. Shared state across connections: the semaphore
(connection count), an `atomic.Uint64` (next connection ID), and a
`map[net.Conn]struct{}` (for `CloseAllConnections`) protected by its own
mutex (`connsMu`).

### Q&A: TCP Network Layer

**Q: What happens to a connection that's idle for a long time?**
A: `SetReadDeadline` is applied before every read, using the configured
`ReadTimeout` (default 30s). If the client sends nothing within that window,
the read returns a timeout error, the server writes an error response, and
closes the connection. This is proven by
`TestServer_ReadTimeoutDisconnectsIdleClient` — which, notably, had to be
written carefully: the *first* read after the deadline doesn't necessarily
error, because the server writes an error message to the client before
closing, so the test loops reading until it actually observes the closure,
rather than asserting the very first read fails.

**Q: Why one goroutine per connection instead of an event loop / epoll-style
multiplexer?**
A: Go's runtime scheduler already multiplexes goroutines onto OS threads
efficiently (goroutines are cheap — a few KB of stack, growable), and the
network poller under the hood *is* an efficient epoll/kqueue-based
multiplexer — you get that benefit for free without writing your own reactor
pattern. One-goroutine-per-connection is idiomatic Go and is what
`net/http`'s own server does. The `MaxConns` semaphore is what keeps this
from being unbounded under load.

**Q: How would you find out if this design's connection-per-goroutine model
becomes a bottleneck at very high connection counts?**
A: I'd load-test with something like `go test -bench` driving many
concurrent short-lived connections, watch goroutine count and memory via
`pprof`, and look specifically at scheduler latency under `GOMAXPROCS`
contention. I haven't needed to do this yet — it's an honest "I'd measure,
not guess" answer.

## 4.3 In-Memory Cache Engine

**What.** `internal/cache` — the actual key-value store. TTL-based expiration
(both lazy, on access, and active, via a background sweep), pluggable
eviction policy (LRU or LFU), and a memory-bounds enforcer.

**Data structures.**
- **The store itself** (`internal/cache/store.go`): a `map[string]*Entry`
  guarded by a mutex, plus an `atomic.Int64` tracking total estimated memory
  bytes (`memBytes`), updated incrementally on every mutation rather than
  recomputed by walking the whole map.
- **LRU** (`internal/cache/eviction.go`): the textbook structure — a
  `container/list.List` (Go's built-in doubly-linked list) for recency order,
  plus a `map[string]*list.Element` for O(1) lookup into that list. `Get`
  moves the accessed element to the front; `Put` does the same, or evicts the
  back of the list (`order.Back()`) when at capacity. **O(1) for both Get and
  Put** — the entire reason a hash map alone isn't enough for LRU is that a
  map has no ordering, so you need the linked list *just* to know what's
  least-recently-used without a full scan.
- **LFU**: tracks an access-frequency counter per key. **The tie-break
  matters and is where a real bug lived** — see below.
- **`evictionTracker` interface**: `Put`/`Get`/`Remove`/`RemoveOldest`/
  `Reset` — this abstraction is what lets `LocalCache.enforceLimits` drive
  eviction externally (by memory pressure or by absolute key count) without
  caring whether the underlying policy is LRU or LFU. Both trackers are
  constructed with an internal capacity of `1<<30` (effectively unlimited)
  so their *own* internal eviction never fires — capacity enforcement is
  entirely the outer `LocalCache`'s job, keeping "what triggers eviction"
  (memory pressure, key-count limit) cleanly separate from "which key gets
  evicted" (the policy).

**The real bug this session found: LFU's tie-break was non-deterministic.**
Every newly-inserted key starts at frequency 1 — the same frequency as any
older key that also happens to have been touched only once. The original
`findMinLocked` (the function that finds the eviction victim: the key with
the lowest frequency) broke ties by whatever order Go's `for key := range
map` happened to iterate in — which Go explicitly randomizes on every run,
specifically to stop people relying on it. That means: **which key gets
evicted under a frequency tie was unpredictable and different on every
process restart.** That's a real correctness bug for a documented "least
frequently used" policy — an operator can't reason about or reproduce
eviction behavior at all. It was actually *found* by a new test,
`TestLocalCache_LFUEvictsLeastFrequentlyUsedFirst`, which kept flaking
intermittently — investigating the flake, rather than just re-running the
test, is what surfaced the real bug underneath it. The fix: a monotonic
`seq`/`clock` counter, so ties break toward the *stalest* entry (lowest
sequence number = touched longest ago) — deterministic, and matches the
intuitive meaning of "least frequently used" better than an arbitrary map
iteration order ever did.

**TTL: lazy vs. active expiration.**
- *Lazy*: `Get` checks the entry's `ExpiresAt` and treats an expired entry as
  a miss, deleting it on the way out. This alone would mean a key that's
  never accessed again after expiring just sits in memory forever, wasting
  space.
- *Active*: a background goroutine (`evictExpired`, driven by a ticker at
  `ExpirationInterval`) periodically samples a batch of keys
  (`ExpirationSampleSize`) and deletes any that are expired — bounded work
  per tick, not an O(n) full-map scan, so it doesn't cause latency spikes on
  a large keyspace.

**Concurrency.** `Store` uses a single mutex around the map (a `RWMutex`
would allow concurrent reads, but the LRU/LFU trackers themselves need to
mutate on *every* access, including reads — `Get` moves an element in the
LRU list — so a plain `Mutex` is the honest choice here, not a missed
optimization). The `memBytes` counter is a separate `atomic.Int64` precisely
so a stats read (`MemoryBytes()`) doesn't need to take the same lock as a
mutation — it's a genuinely independent piece of state.

**A subtle flaky-test story worth knowing:** `TestActiveExpirationShutdown`
used to occasionally fail. The test captured a "before" memory size, called
`Shutdown()`, then compared it to an "after" size — but the "before" snapshot
was taken *before* the active-expiration sweeper's own last in-flight tick
had necessarily finished, so it was racing against legitimate, correct
background work. The fix was simply to capture the "before" baseline *after*
`Shutdown()` returns (at which point the sweeper goroutine is guaranteed
stopped) — a good example of a flaky test not always meaning there's a
concurrency bug in the code; sometimes it means the *test itself* has an
ordering assumption that's wrong.

### Q&A: Cache Engine

**Q: Why LRU/LFU as an injected interface instead of hard-coding one policy?**
A: Different workloads want different eviction behavior — LRU suits
recency-biased access patterns (a typical web session cache), LFU suits
workloads where a small set of "hot" keys are accessed far more often
regardless of recency (e.g., a popular product ID that's read constantly
while other products come and go). Making it configurable
(`EvictionPolicyFromString`, which fails loudly on an unrecognized string
rather than silently defaulting — matching the project's own "no silent
misconfiguration" convention used elsewhere, like WAL sync modes) means an
operator picks based on their actual workload.

**Q: What's the complexity of eviction under memory pressure — is it O(1)?**
A: Finding the eviction victim in LRU is O(1) (it's always `order.Back()`).
In LFU it's **not** O(1) in this implementation — `findMinLocked` scans all
tracked frequency buckets to find the minimum, which is O(number of distinct
frequency values currently in use), not O(number of keys), but still not
constant. A textbook fully-O(1) LFU (the classic "LFU cache" algorithm)
keeps a doubly-linked list of frequency buckets, each containing a
doubly-linked list of keys at that frequency, so eviction is always
"the back of the lowest frequency bucket" — O(1). That's a legitimate
"how would you optimize this further" answer if asked.

**Q: How do you estimate memory usage per entry without measuring actual heap
allocation?**
A: `internal/cache/entry.go`'s `estimatedSize(key, value)` computes
`len(key) + len(value) + entryOverheadBytes` (a constant, 64 bytes, standing
in for Go's own map-entry/struct overhead). It's an estimate, not an exact
figure from `runtime.MemStats` — exact per-allocation accounting in Go isn't
practical without external tooling, and an estimate that's honestly
approximate and consistently applied is more useful for a memory *limit*
than no accounting at all.

## 4.4 Consistent Hashing

**What.** `internal/hashring/ring.go` — decides which node owns a given key,
using a hash ring with virtual nodes so that adding/removing a node only
reshuffles a small, bounded fraction of keys instead of the entire keyspace.

**Why not just `hash(key) % number_of_nodes`?**
Because that's the whole problem with naive modulo-sharding: if you go from 5
nodes to 6, `hash(key) % 5` and `hash(key) % 6` disagree for almost every key
— nearly the entire keyspace remaps to a different node simultaneously. For a
cache, that means a near-total cache-miss storm the moment you scale the
cluster. Consistent hashing fixes this: nodes and keys are placed on the same
circular hash space (0 to 2³²−1), and a key belongs to the first node at or
after its position going clockwise. Adding a node only takes over the
narrow arc of keyspace between its new position and the previous node's
position — everything else stays exactly where it was.

**Why *virtual* nodes (150 per physical node), not one point per node?**
With only one point per physical node, the arcs each node owns are
wildly uneven by chance (whichever node's random hash position happens to sit
next to a big gap owns a disproportionate share of keys) — and when a node
is removed, its *entire* arc goes to exactly one neighbor, creating a hot
spot. Giving each physical node 150 *virtual* positions, scattered around the
ring, averages this out: removing a node redistributes its keys across many
different neighbors roughly evenly, not dumping it all on one.

**The exact algorithm (`internal/hashring/ring.go`):**
```go
func (hr *HashRing) hash(key string) uint32 {
    h := uint32(2166136261)          // FNV-1a 32-bit offset basis
    for i := 0; i < len(key); i++ {
        h ^= uint32(key[i])
        h *= 16777619                 // FNV-1a prime
    }
    return h
}
```
This is **FNV-1a**, a simple, fast, non-cryptographic hash — cryptographic
strength is irrelevant here; you just need a good, uniform distribution over
32 bits and speed, since this runs on every single key lookup.

`AddNode(nodeID)` computes 150 positions (`hash("nodeA#0")`, `hash("nodeA#1")`,
... `hash("nodeA#149")`), inserts them all into a sorted slice (`ring
[]uint32`), and records `nodes[position] = nodeID` in a map. `GetNode(key)`
hashes the key and does a **binary search** (`sort.Search`, Go's
`bsearch`-equivalent) for the first ring position ≥ that hash — wrapping
around to index 0 if the key's hash is past the last position (the ring is
circular). **O(log(nodes × 150)) per lookup**, O(nodes × 150 × log(nodes ×
150)) to rebuild the sorted slice on membership change (via `sort.Slice`).

**Concurrency.** `HashRing` uses a `sync.RWMutex` — `GetNode`/`GetNodes` take
a read lock (many concurrent lookups are safe simultaneously since nothing
mutates), `AddNode`/`RemoveNode`/`ReplaceNode` take a write lock (membership
changes are rare relative to lookups, so optimizing for concurrent reads is
the right trade-off).

**`ReplaceNode` — a subtlety worth knowing:** when a replica is promoted to
replace a dead primary, its ring entry doesn't just get relabeled — the dead
node's *virtual-node positions* are transferred to the new node's ID, and
critically, this is **additive**: if the new node already owned some
positions of its own before the promotion, those are preserved, and the
dead node's positions are added on top. The promoted node ends up owning
both its original key range and the dead primary's former range — which is
exactly correct: those keys need an owner, and the promoted node is the
best-positioned candidate (it already had the data as a replica).

### Q&A: Consistent Hashing

**Q: Walk me through what happens to the ring when a 6th node joins a 5-node
cluster.**
A: The new node's 150 virtual positions get inserted into the sorted ring.
For every one of those 150 insertion points, the *single* physical node that
previously owned the arc ending at that point now only owns up to the new
virtual node's position — the remainder of that arc transfers to the new
node. Averaged over 150 insertion points scattered randomly around the ring,
this works out to roughly 1/6th of the total keyspace moving to the new
node, drawn roughly evenly from all 5 existing nodes rather than from just
one neighbor.

**Q: What's the actual mechanism that *moves* the data, not just the ring's
bookkeeping?**
A: The ring only decides *ownership* — it doesn't move bytes. That's a
separate migration process (`internal/hashring/rebalance.go`) that computes
which keys fall in the newly-affected range (`GetAffectedRange`) and
transfers them from old owner to new owner, with a redirect mechanism
(`MarkKeyMigrated`/`RedirectTarget`, a 5-minute TTL) so a client whose
routing view hasn't caught up yet still gets forwarded to the right place
instead of a false cache miss.

**Q: Why FNV-1a and not something like MurmurHash or SHA-256?**
A: Cryptographic hashes (SHA-256) are needlessly expensive for this — you're
not defending against an adversary crafting hash collisions here (and even
if you were, that's a separate DoS-hardening concern, not what the ring
itself needs to solve), you just need speed and a reasonably uniform
distribution. FNV-1a is a standard, well-understood choice for this kind of
non-cryptographic hashing; MurmurHash or xxHash would also be reasonable
and slightly faster in some benchmarks — this is a place where the specific
choice matters less than picking *something* fast and uniform and being
consistent about it everywhere the same ring math needs to be reproduced
(notice `internal/chaostest/ring.go`, the chaos-test harness's independent
verification tool, deliberately mirrors this *exact* same FNV-1a algorithm
and 150-vnode count, in a comment explicitly calling out that it "mirrors
internal/hashring exactly" — because if the test harness's idea of "who
should own this key" ever drifted from the real ring's algorithm, every
migration-correctness test built on top of it would be silently checking
against the wrong expected owner).

## 4.5 Replication

**What.** `internal/replication` plus the replication-related methods in
`internal/network/handler.go` (`replicateWrite`, `handleReplicate`,
`handleReplicaSync`) — propagates writes from a shard's primary to its
replicas, tracks how far behind each replica is, and handles gaps when a
replica falls behind or reconnects.

**The core design decision: per-shard replication, not full-database
replication.** Because HydraCache shards via consistent hashing, there is no
single "the leader" for the whole dataset — each key has its own primary
(whoever the hash ring currently assigns it to) and that primary's own set of
replicas. `replicateWrite` checks `hashring.PrimaryNode(key)`; if the local
node isn't the primary for that key, it does **not** replicate the write via
this path (see Part 7 for the real, honest limitation this creates if a
client writes to the *wrong* node).

**Async vs. sync replication.**
- **Async (default):** the client's write returns as soon as it's durable
  *locally* (WAL + in-memory mutation done); replication to replicas happens
  in background goroutines afterward, and the client never waits for it.
  Matches how most production caches actually operate — replication lag is
  a real, measured, ongoing fact of life, not something every write blocks
  on.
- **Sync:** the client's write blocks until at least `AckCount` replicas
  confirm (bounded by `SyncTimeout`) — mirroring the *reporting* semantics of
  Redis's `WAIT` command: the local write has already happened either way
  (there's no safe way to "undo" it once other readers may have already
  observed it), sync mode only tells the client whether it was *sufficiently
  replicated* before returning, surfacing an error like "applied locally but
  under-replicated" if the bound isn't met in time — an honest signal, not a
  rollback.

**Epoch fencing — the mechanism that makes replication safe across topology
changes.** Every replicated operation carries the sender's current
*topology epoch* (not the same thing as the election term — see 4.7's Q&A on
this exact distinction). A replica tracks the highest epoch it's seen for
each shard (`CheckAndAdvanceEpoch`) and **rejects** an incoming op whose
epoch is *behind* that — because a lower epoch means the sender's view of
"who owns this shard" is stale (a membership change happened after the
sender last knew about it), and applying its write could silently
resurrect data that a newer, correct primary already knows is wrong.

**Gap detection and catch-up.** Each shard's replication stream tracks a
monotonic sequence number per operation. When a replica receives an op
whose sequence number *skips ahead* of what it's already applied
(`op.Seq > last+1`), it knows it missed one or more prior ops — it pulls the
missing range from the primary via `REPLICA_SYNC` and applies them in order
*before* applying the new one, rather than either dropping the gap silently
or applying out of order.

**A known, honestly-scoped limitation worth naming if asked:** the
`REPLICA_SYNC` *pull* path (a reconnecting replica proactively asking "what
did I miss since sequence N?") is fully implemented on the primary side
(`handleReplicaSync`) but has **no caller** anywhere in the codebase — the
initial sync for a newly-added replica uses a different, primary-*push*
mechanism instead. This is explicitly documented in the code itself as
"KNOWN SCOPE BOUNDARY — PULL PATH UNREACHABLE" rather than left as a silent
gap. Being able to point at your own code and say "I know this exists,
here's exactly why it's not wired up yet, and here's what wiring it up would
take" is a strong answer if an interviewer probes for gaps.

### Q&A: Replication

**Q: What happens if a client connects to a node that isn't the primary for
the key it's writing?**
A: Today, the write still happens on whichever node the client connected to
— it succeeds locally, but it is *not* replicated anywhere, and no other
node's cache will ever see it (except indirectly, if a later rebalance
migrates that key's ownership and the migration mechanism happens to touch
it). This is a real, honestly-documented limitation, not a hidden bug — see
Part 7. It means clients today are expected to be "dumb" about routing (like
`cmd/cli` — connect to one fixed address), which trades off the elegance of
sharding-transparent writes for not having built (yet) either a Redis
Cluster-protocol MOVED/ASK redirect mechanism or a fully consistent
server-side write-forwarding layer.

**Q: How do you decide how many replicas is enough?**
A: That's the `ReplicationFactor` on the `Locator` — a configured number
(default in this project's examples is 2–3) representing how many nodes
(including the primary) should hold each key. It's a classic trade-off:
higher replication factor means better durability and read-availability
under node failure, at the cost of more storage and more replication
traffic per write.

**Q: What's the difference between "epoch" here and the "term" in leader
election (4.7)?**
A: They track *different facts* and are deliberately not conflated. The
*election term* answers "who is the current cluster-coordinator" — a
node-level concept. The *topology epoch* answers "how many times has cluster
membership/shard ownership changed" — and it's what fences the *data path*
(replication). They could in principle be the same number if the design were
"whoever wins the election also owns all the data," but HydraCache
deliberately isn't that design — data ownership is per-shard via consistent
hashing, so conflating a single election term with per-shard data fencing
would be actively wrong, not just redundant.

## 4.6 Failure Detection (Phi-Accrual)

**What.** `internal/heartbeat/detector.go` — decides whether a peer node is
alive, suspect, or dead, based on the actual statistical timing of its past
heartbeats rather than a single fixed timeout.

**Why not just "no heartbeat for 5 seconds = dead"?**
A fixed timeout is either too aggressive (a node on a network with normal
jitter gets falsely marked dead the moment one heartbeat is a bit late,
triggering an unnecessary and disruptive failover) or too lax (set the
timeout high enough to tolerate jitter, and now a *genuinely* dead node takes
much longer to detect than it needs to on a normal, low-jitter network). The
right timeout depends on how *variable* that particular link's timing
actually is — which is exactly what phi-accrual measures.

**The exact math** (`HeartbeatEntry.Phi`, `internal/heartbeat/detector.go`):
1. Keep a rolling window of recent inter-arrival intervals (bounded by count
   — `WindowSize`, default 1000 — *and* by age — `MaxSampleAge`, default 10
   minutes, so an old jitter profile doesn't keep influencing the model
   forever after conditions change).
2. Compute the sample mean and variance of those intervals.
3. Given `elapsed` = time since the last heartbeat actually arrived, compute:
   ```
   phi = -log10( 0.5 * erfc( (elapsed - mean) / (stddev * sqrt(2)) ) )
   ```
   `erfc` is the complementary error function — this expression is exactly
   "the probability, under a normal distribution fit to past intervals, that
   we'd still be waiting this long for a heartbeat if the node were actually
   fine." As `elapsed` grows far past the historical mean, that probability
   shrinks toward zero, and `-log10` of a shrinking probability grows toward
   infinity — so `phi` increases the longer you wait, accelerating the
   further you are past what history says is normal.
4. A node is **suspect** once `phi` crosses `PhiThreshold` (default 8.0 — a
   phi of 8 corresponds to roughly a 1-in-10⁸ chance the node is actually
   fine, if you trust the normal-distribution model). A node is declared
   **dead** only after it has stayed continuously suspect for
   `SuspectTimeout` (default 5 seconds) — a second layer of debouncing on
   top of the statistical model, so a single momentary phi spike doesn't
   immediately trigger a costly failover.
5. **Practical floor:** if a node's heartbeats have been extremely regular
   (tiny stddev, e.g. 1ms jitter on a 1-second interval), the formula would
   become hypersensitive — a mere 100ms of extra delay could blow phi to
   infinity. The code floors `stddev` at 10% of the mean specifically to
   prevent this over-sensitivity.

**Injectable clock.** `Clock` is an interface (`Now() time.Time`), with
`realClock` as the production implementation and a fake, controllable clock
used in tests — this is what makes phi-accrual's timing-dependent behavior
*deterministically testable* at all; without it, testing "does this correctly
detect a slow node" would require actually sleeping in tests, making them
slow and flaky.

**Concurrency.** `Detector` holds a `map[string]*HeartbeatEntry` (one per
tracked peer) behind a `sync.RWMutex`. Each `HeartbeatEntry`'s own state
(`samples`, `suspectSince`) is only ever touched while holding the
detector's lock — there's no separate per-entry lock, keeping the locking
model simple (one lock, briefly held) rather than risking lock-ordering bugs
from many fine-grained locks.

### Q&A: Failure Detection

**Q: Why does `suspectSince` exist — why not just fire the "node is suspect"
callback every time you check and phi is over the threshold?**
A: Because the detector is checked on a tick (a background loop), not just
once — if you fired the callback every tick a node stays suspect, you'd spam
whatever's listening (e.g., a gossip/promotion trigger) repeatedly for what
is conceptually one ongoing event, not many. `suspectSince` is set the moment
phi *first* crosses the threshold and cleared on recovery, so the "node
became suspect" signal fires exactly once per episode — a state transition,
not a level check.

**Q: What's a concrete scenario where phi-accrual gives a different answer
than a fixed timeout would?**
A: A node on a network path with high but *consistent* jitter — say,
heartbeats normally arrive every 1s ± 400ms. A fixed 2-second timeout would
false-positive constantly on this link even though it's behaving completely
normally for itself. Phi-accrual learns that 400ms of jitter is this link's
normal behavior (large stddev in its own model) and doesn't get suspicious
until the wait is far outside *that* link's own historical pattern, not some
global fixed number.

**Q: Is phi-accrual itself a consensus mechanism?**
A: No — it's a purely local, per-peer signal (every node runs its own
detector, watching its own view of every other node's heartbeat timing).
Different nodes can legitimately disagree about whether a given peer is
suspect at any instant, especially during a partial network partition. It
feeds *into* higher-level decisions (gossip dissemination, promotion
triggers) but is not itself a distributed agreement protocol.

## 4.7 Leader Election (Raft-Style)

**What.** `internal/election/election.go` — a simplified Raft-style election:
persisted terms, a pre-vote phase, quorum computed from live membership, and
a leader lease.

**The most important thing to understand — and say out loud, unprompted, if
asked about this — is what this election is *for*.** The package's own
top-of-file comment says it directly: *"HydraCache's data path is sharded by
consistent hashing rather than owned by a single whole-cluster leader, so
this package is a general-purpose primitive... its term is not used as the
per-write fencing token — see internal/replication for the per-shard epoch
fencing that protects the actual data path."* In other words: this election
answers "which single node currently holds cluster-coordinator status" (a
node-level fact, wired in `cmd/server/main.go`), and is a *completely
separate concept* from "who owns this shard's data," which is the hash
ring's and replication's job (4.4, 4.5). A candidate who conflates these two
things in an interview answer will sound like they don't actually understand
their own system's architecture — this is one of the highest-value
distinctions to have crisp and ready.

**States:** `Follower`, `Candidate`, `Leader` — the standard Raft state
machine.

**Term persistence.** Every node persists its current term and who it voted
for to disk (`TermStore`, backed by an atomic file rename — write to a temp
file, then rename over the real file, so a crash mid-write never leaves a
half-written, corrupt term file) and reloads it on startup
(`election.New` calls into the store immediately). Why persist this at all?
Because Raft's core safety property — *a node never votes for two different
candidates in the same term* — only holds if a restarted node remembers what
it already voted for. Without persistence, a crash-and-restart could vote
again in a term it already voted in, potentially enabling two leaders to
both believe they won the same term.

**Pre-vote.** Before actually starting a real election (incrementing its own
term and requesting votes), a candidate first runs a *pre-vote* round: "if I
were to start an election, would you vote for me?" — without incrementing
its term yet. This solves a specific, real Raft pathology: a node that's
partitioned away from the cluster (so it never hears real leader heartbeats)
will keep timing out and incrementing its term over and over, building up a
very high term number while isolated. The moment it reconnects, that
artificially inflated term would let it disrupt a perfectly healthy existing
leader (higher term wins in Raft) even though it has no actual chance of
winning an election with an unreachable minority. Pre-vote means a
partitioned node's repeated timeout attempts never actually bump the *real*
term number, because it never gets enough pre-votes to proceed to a real
election in the first place — so reconnecting doesn't destabilize anything.

**Quorum from live *known* membership, not live *reachable* membership.**
The `PeersFunc` config comment is explicit about this: it must return the
full known cluster membership, *including currently-unreachable nodes* — not
just the nodes this node can currently talk to. Why does that distinction
matter so much it's called out in a doc comment? Because if quorum were
computed only from *reachable* peers, a minority partition could compute
quorum among just its own members (since from its own point of view, that's
"everyone it can see") and incorrectly elect its own leader — a split-brain.
Requiring quorum against the *true* cluster size means a minority partition
mathematically cannot reach quorum, no matter how confident it is locally.

**Leader lease.** A leader tracks `lastQuorumAck` — the last time a
heartbeat round it sent actually reached quorum acknowledgment. If that
goes stale past `LeaseTimeout` (default 1 second, deliberately well above
the heartbeat interval to tolerate jitter/GC pauses), the leader steps down
on its own — so a leader that's been silently partitioned away from the
majority (but hasn't crashed, and would otherwise keep believing it's
leader forever) voluntarily gives up leadership instead of continuing to
act on stale authority.

**Graceful resignation.** `Resign()` lets a leader voluntarily step down
(used during clean shutdown in `cmd/server/main.go`, right before `cancel()`
is called) rather than making the rest of the cluster wait out a full
lease-timeout-driven detection of "the leader silently disappeared." This is
purely an optimization for the *clean shutdown* case — a crash still relies
on lease expiry/heartbeat timeout, since a crashing process obviously can't
run its own graceful-shutdown code.

**Concurrency.** `Election` guards its core state (`state`, `term`,
`votedFor`, timestamps) behind a `sync.RWMutex`. Two `atomic.Bool` flags
(`electing`, `heartbeating`) prevent overlapping election attempts or
overlapping heartbeat rounds from running concurrently with themselves — a
cheap, lock-free way to say "don't start a second one of these while one is
already in flight."

### Q&A: Leader Election

**Q: If this election isn't deciding who owns the data, what actually breaks
if it's not running at all — e.g., single-node mode?**
A: Nothing on the client's read/write path — `PeersFunc` defaults to
returning no peers, meaning a single node trivially has quorum of 1 with
itself, becomes leader instantly, and every client operation works exactly
the same either way. What the coordinator role is actually used *for* in
this codebase (via `SetElection`/`SetEpochSource` wiring in
`internal/network/handler.go`) is answering "is this node currently the
cluster's leader" for status/observability purposes (e.g. what the
dashboard's `role` field and `CLUSTER INFO`/`HELLO`'s `role` field report)
— it is deliberately *not* load-bearing for whether any GET/SET succeeds.

**Q: What's the actual failure mode pre-vote prevents, in concrete terms?**
A: Without pre-vote: node C gets partitioned away from a healthy 5-node
cluster (nodes A–E, A is leader). C never hears A's heartbeats, so C's
election timeout keeps firing every few hundred milliseconds, incrementing
C's own term each time — after even a short partition, C's term might be
100+ higher than the real cluster's term (still at, say, 3). The instant the
partition heals, C sends a vote request or heartbeat carrying that
massively higher term number, and Raft's rule "a higher term always wins"
would force A to step down and the cluster to run a real, disruptive
election — purely because C was isolated, not because A was actually
unhealthy. Pre-vote prevents C's term from ever inflating in the first
place, since it never secures enough pre-votes (a minority of one) to
advance to a real term increment.

**Q: Why is `RPCTimeout` a separate config value from `ElectionTimeoutMax`?**
A: They bound different things. `ElectionTimeoutMax` (default 300ms, with
`ElectionTimeoutMin` at half that, and the actual timeout randomized between
them — the randomization itself is a classic Raft technique to reduce the
chance of two candidates timing out simultaneously and splitting the vote)
is how long a follower waits without hearing from a leader before it decides
to start its own election. `RPCTimeout` (default 200ms) bounds any single
outbound vote/heartbeat network call — without this, one unreachable or
merely slow peer could stall an entire election round or lease-renewal
attempt indefinitely, regardless of how the overall election timing is
configured.

## 4.8 Gossip / Cluster Membership

**What.** `internal/cluster/gossip.go` — disseminates membership state
(who's alive, who's suspect, who's dead, who left) between nodes without
every node needing to talk to every other node directly on every update —
a SWIM-inspired design (Scalable Weakly-consistent Infection-style process
group Membership).

**The core idea: infection-style dissemination.** Instead of a node
broadcasting its state change to the entire cluster, it periodically gossips
its current view of the world to a small number of *random* peers. Each of
those peers merges what it heard into its own view and, on its next gossip
round, passes the (possibly updated) information along to a different
random set of peers. Information spreads through the cluster the way a
rumor — or an infection — spreads through a population: exponentially, via
repeated random contact, without needing any single node to know the full
membership list to reach everyone, and without a linear "tell everyone
directly" cost that doesn't scale.

**Incarnation numbers and self-refutation** (`Gossip.selfRefute`) — this is
the single most interesting mechanism in this subsystem and worth having a
sharp, ready explanation for. The problem it solves: gossip is inherently
*eventually* consistent and based on stale, indirect information — it's
entirely possible for a peer's gossip message to claim "node X is dead" when
node X is, from X's own point of view, completely fine (e.g., X had a
transient network blip that made some *other* node suspect it, and that
suspicion is now spreading). Without a way to correct this, a healthy node
could get permanently and incorrectly marked dead by a rumor that's stale by
the time it arrives. The fix: every node tags its own membership record with
an **incarnation number** — a counter *it* controls and increments. If node
X receives a gossip message claiming X itself is dead or has left, X bumps
its own incarnation number and re-announces itself as alive at the new,
higher incarnation. Since a higher incarnation always wins over a lower one
for the same node ID (this is `Gossip.Merge`'s comparison rule), X's
self-refutation *outcompetes* and overrides the stale "X is dead" rumor as
it continues to spread — the true, current state wins out over the stale
one, even though gossip itself has no global ordering guarantee.

**Why does this matter for the partition-and-heal chaos scenario
specifically?** After a network partition heals, a node that was isolated
(and got marked dead/suspect by the majority side while it was unreachable)
needs *multiple rounds* of gossip to fully reconcile: it has to receive the
stale "you're dead" rumor, self-refute by bumping its incarnation, and have
*that* refutation propagate back out to every node that held the stale
belief — which is why `internal/chaostest`'s partition-heal scenario
explicitly waits up to 90 seconds (much longer than normal gossip
convergence) for the cluster to report all nodes healthy again after a heal
— this is a real, measured property of the system, not an arbitrary test
timeout.

**Concurrency.** `GossipTable` (the underlying storage for gossip state) and
`Gossip` itself protect their state with mutexes; `incarnation` is a
dedicated `atomic.Uint64` since it's read and compared far more often than
the rest of a member's record and benefits from lock-free access.

### Q&A: Gossip / Cluster Membership

**Q: What's the difference between what gossip decides and what the
phi-accrual detector (4.6) decides?**
A: Phi-accrual is a *local, per-node opinion* about one specific peer's
liveness, based purely on that node's own observed heartbeat timing to that
peer — it doesn't involve any communication about *other* nodes' opinions.
Gossip is the *dissemination* mechanism — it's how one node's local opinion
(informed by its own phi-accrual detector, among other things) becomes
known to the rest of the cluster, and how the cluster's collective view
eventually converges, even though different nodes may transiently disagree
during the process.

**Q: What happens if two nodes gossip with each other about a third node and
have conflicting information?**
A: `Gossip.Merge` resolves this by incarnation number and state precedence
rules (e.g., a later incarnation always wins regardless of claimed state;
for the *same* incarnation, certain state transitions like alive→suspect are
allowed to override the reverse). This is exactly the kind of
last-writer-wins-with-a-twist conflict resolution that gossip protocols need
in place of true synchronization — there's no lock you could take across
two independent nodes' local views.

**Q: Why not just have every node ping every other node directly instead of
gossiping?**
A: That's O(n²) total messages across the cluster for every full round of
health checks, which doesn't scale as membership grows. Gossip's
"tell a few random peers, let it spread" approach means the *per-node*
message cost stays roughly constant regardless of cluster size, while the
information still reaches everyone in roughly O(log n) rounds — a classic
scalability trade-off (slightly higher latency to full convergence, in
exchange for message cost that doesn't grow quadratically).

## 4.9 Write-Ahead Log & Persistence

**What.** `internal/persistence/wal.go` — durability. Every mutating command
is appended to an on-disk log *before* it's applied to the in-memory cache,
so a crash can never lose an acknowledged write, and periodic snapshots keep
the log from growing forever and keep restart time bounded.

**Why write the WAL entry *before* mutating memory, specifically?**
Because the only two possible crash points are "before the WAL write" and
"after the WAL write, before/during the memory mutation" — and ordering it
this way makes both of those safe:
- Crash before the WAL write completes → the write never happened at all,
  from any observer's perspective (the client never got an OK, and nothing
  is in the log to replay). No partial state.
- Crash after the WAL write but before the memory mutation finishes → on
  restart, replaying the WAL reproduces exactly the mutation that was about
  to happen. Also no partial state — the outcome is *as if* the mutation had
  completed.

If the order were reversed (mutate memory first, log second), a crash
between those two steps would leave the in-memory state changed but with no
record of it in the log — the change would be silently lost on restart with
no way to detect it ever happened, which is exactly the failure mode a WAL
exists to prevent.

**CRC-validated entries and torn-tail recovery.** Each WAL entry is
checksummed (CRC32) on write. On restart, entries are replayed in order,
verifying each checksum; a corrupt entry — most commonly a **torn write**,
where the process crashed mid-write to an entry and the last entry on disk is
truncated/incomplete — is detected by a checksum mismatch. The recovery
strategy for a torn tail: **close the file, `os.Truncate` it to drop the
corrupt trailing bytes, then reopen** — deliberately *not* calling
`file.Truncate()` directly on an already-open handle. Why the extra
close/reopen dance? This project runs on Windows as well as Linux/macOS in
CI, and Windows has stricter file-handle semantics around files opened with
`O_APPEND` — truncating via a handle that's still open in append mode hits
access-rights quirks on Windows that don't exist on POSIX systems. Closing
first, truncating the closed file by path, then reopening sidesteps that
entirely, and works identically on every platform — a genuinely
platform-driven correctness fix, not stylistic preference.

**Sync modes** — a real, deliberate durability/performance trade-off exposed
as configuration, not hidden:
- `SyncAlways`: `fsync` after every single write. Maximum durability
  (survives a full OS crash, not just a process crash), lowest throughput.
- `SyncEverySec`: a background goroutine `fsync`s at most once per second,
  decoupled from write volume — bursts of writes don't each pay the fsync
  cost, but you can lose up to ~1 second of the most recent writes on a hard
  crash (not a clean process crash — the *process's own* writes are still in
  the OS's page cache and would survive a process crash; this mode's actual
  exposure is specifically to an OS-level crash or power loss before the
  next periodic fsync).
- `SyncNever`: no explicit fsync at all — durability is entirely whatever the
  OS's own write-back policy happens to provide. Highest throughput, weakest
  guarantee.

Like the eviction-policy config, an unrecognized sync-mode string
(`SyncModeFromString`) is a hard startup error, not a silent fallback to a
default — a typo in config should fail loudly, not silently pick different
durability semantics than the operator asked for.

**Snapshots.** Periodically (`SnapshotInterval`), the entire current cache
state is written to a snapshot file, and the WAL can then be truncated up to
that point (everything before the snapshot is redundant — the snapshot
already captured its effect). This bounds both on-disk log size and, more
importantly, **restart time**: without snapshots, recovering from a WAL that
had been growing since the process was first started would mean replaying
its *entire* history on every restart, which only gets worse over the
server's lifetime.

### Q&A: WAL & Persistence

**Q: What's the actual recovery sequence on startup?**
A: `internal/persistence/recovery.go`: load the most recent valid snapshot
(if any) to restore a baseline state, then replay every WAL entry with a
sequence number *after* that snapshot's sequence number, in order,
validating each entry's checksum and stopping cleanly (truncating the torn
tail) at the first corrupt entry rather than erroring out the whole startup.

**Q: If `SyncEverySec` can lose up to a second of writes, why would anyone
choose it over `SyncAlways`?**
A: Because `fsync` is genuinely expensive — it's a synchronous round-trip to
physical storage, and doing it after every single write caps your write
throughput at your storage device's fsync latency, not your CPU's. Most
production caches (and databases, for that matter — this is the same
trade-off Redis's own `appendfsync everysec` setting makes) accept "lose at
most ~1 second of the most recent writes in the rare event of a hard crash
or power loss" in exchange for dramatically higher sustained write
throughput, because a *cache* in particular is often re-derivable from its
system of record anyway (see 4.14's read-through pattern) — losing a second
of cached writes is a much smaller deal than losing a second of a primary
database's writes would be.

**Q: How would an operator recover if the WAL file itself were deleted or
corrupted beyond the torn-tail-truncation the code already handles?**
A: The most recent snapshot is still a valid, complete recovery point on its
own — the operator would lose only whatever writes happened strictly after
that snapshot. This is exactly why snapshots exist as a *second*, independent
durability artifact, not purely a performance optimization for restart
speed.

## 4.10 Security (AUTH / ACL / TLS)

**What.** `internal/auth` (ACL/authentication logic) plus the AUTH-gating
logic in `internal/network/handler.go`, and TLS/mTLS in
`internal/network/tls.go` (already covered in 4.2 from the network-layer
side — this section is the authentication/authorization side).

**AUTH.** A client sends `AUTH password` or `AUTH username password`.
`ACL.Authenticate` checks the credential using **constant-time comparison**
(`subtle.ConstantTimeCompare`) — deliberately, not just `==` on strings.
Why? A naive string comparison (`==`, or most languages' default string
equality) short-circuits at the *first mismatched byte* — which means the
time it takes to reject a wrong password leaks information about *how many
leading characters were correct*, in principle allowing an attacker to guess
a password one byte at a time via careful timing measurements (a timing
side-channel attack). Constant-time comparison always examines the full
length regardless of where a mismatch occurs, so the comparison's duration
reveals nothing about how close a guess was.

**Password storage.** Supports a `sha256:<hex>` prefix convention for
storing a hash instead of a plaintext password in config — so an operator
doesn't have to keep the real password sitting in a config file at rest,
only its hash.

**ACL — per-user command and key-pattern permissions.** Each configured user
has an allow-list of commands and an allow-list of key glob patterns (matched
via `path.Match`, the same glob syntax used for filesystem paths — e.g.
`session:*` matches any key starting with `session:`). `Allowed(username,
command, key)` is checked on every command; commands with no natural
single-key argument (like `PING`) are gated by command-permission alone.

**The critical design decision that makes clustering keep working once AUTH
is enabled:** inter-node RPCs (`GOSSIP`, `REPLICATE`, `REPLICA_SYNC`,
`ELECTION_VOTE`, `ELECTION_HEARTBEAT`) are **exempt** from the client ACL
check (`isInterNodeCommand`, checked first in `HandleAuthenticated` before
any auth logic runs at all). Why is this necessary rather than just a
convenience? Because a peer node connecting to another node for gossip or
replication **never calls `AUTH`** — there's no code path where it would.
If these commands weren't exempted, turning on client authentication would
silently and completely break clustering the moment it's enabled, since
every inter-node RPC would get rejected with `NOAUTH`. The trust model here
is deliberately explicit: node-to-node trust is (or, honestly, *would be*
— see Part 7) TLS's job, not a per-connection client-session AUTH check —
those are different trust boundaries (client-to-server identity vs.
node-to-node cluster membership) and conflating them would be a real design
mistake, not just a missing feature.

**`HELLO`'s inline AUTH clause.** Modern Redis clients (`go-redis` in
particular) don't necessarily send a bare `AUTH` command — by default they
negotiate protocol version via `HELLO`, optionally with credentials folded
into that same call (`HELLO 2 AUTH user pass`). `handleHello` supports this
exact inline form, and — like bare `AUTH` — is reachable *before* the
session is authenticated (otherwise no client using this login path could
ever authenticate at all, a circular deadlock in the design).

**TLS/mTLS** (detailed in 4.2): server-side `tls.Listen`, with
`RequireClientCert` enabling mutual TLS for the inbound listener, and a
single shared, swappable outbound TLS config for every dial the process
makes as a client (to peers, or forwarding a redirected GET).

### Q&A: Security

**Q: Walk me through why `AUTH` sent with no ACL configured returns a
specific, different error than "unknown command."**
A: Real Redis's exact behavior for this case is `"ERR Client sent AUTH, but
no password is set. Did you mean AUTH <username> <password>?"` — and this
project matches that precisely, rather than falling through to a generic
"unknown command 'AUTH'" (which is what would happen if `AUTH` weren't
special-cased at all when no ACL is wired up). This was a specific
compatibility fix made during this session's protocol-compatibility audit:
getting a misleading error for a command that *is* real, just not
applicable in this configuration, is confusing for anyone debugging a
connection issue, and matching the exact real-Redis message means any
tooling that pattern-matches on that string behaves correctly against this
server too.

**Q: Is there any authentication on the metrics/admin HTTP endpoints
(`/api/cluster`, `/api/stats`, `/metrics`)?**
A: No — and this is worth naming proactively as a real, current limitation
rather than waiting to be caught not knowing it. Those endpoints are served
on a separate HTTP mux with no AUTH/ACL check at all. In a real production
deployment, this would need to sit behind a network boundary (a private
network, a reverse proxy requiring its own auth, a firewall rule) rather
than being exposed the same way the RESP port is — the same way most
Prometheus-scraped `/metrics` endpoints in the wild are typically protected
by network topology rather than an application-level credential.

**Q: What would you need to add to make node-to-node trust actually
enforced by TLS, not just "TLS is available if you turn it on"?**
A: Mutual TLS with each node's certificate identity actually checked against
an expected peer identity (today, `RequireClientCert` proves *a* valid
client certificate was presented, but the handler doesn't yet check *whose*
certificate it is against a peer allow-list) — and a decision about whether
that identity check happens at the TLS layer (via a custom
`VerifyPeerCertificate` callback) or via a separate application-level
handshake once the TLS connection is already established.

## 4.11 Metrics & Observability

**What.** `internal/metrics` — counters (requests, hits, misses, evictions),
gauges (keys, memory, connections, alive/total nodes), per-command latency
tracking, and two export formats: a JSON snapshot and a real Prometheus
text-format exporter.

**The counters and gauges.** `Collector` holds a set of `atomic.Int64`
fields, incremented (`IncrRequests`, `IncrHits`, ...) or set directly
(`SetKeys`, `SetMemory`, ...) from various call sites — notably, a periodic
background goroutine in `cmd/server/main.go` pushes fresh values from the
cache engine and cluster topology into the collector every 5 seconds, rather
than the collector polling those subsystems itself, keeping the dependency
direction one-way (the collector doesn't need to know how to read cache/
cluster internals, callers push their own numbers in).

**The latency histogram — this session's own audit finding, worth having
ready as a concrete "I found a real bug in my own code" story.** A method
called `RecordLatency(method, duration)` existed, was fully unit-tested in
isolation, and yet was **never called by any production code path** — the
exact same "constructed, never wired in" pattern this same audit found
twice elsewhere in the project (a `logging` package that was built,
tested, and then discarded with `_ = logger` in `main.go`; a `pubsub.Broker`
constructed and immediately thrown away with `_ = broker`). Beyond that, even
if it *had* been called, the underlying `latencyBucket` struct only tracked
a running total and count (enough for an average) and a max — not enough to
answer "what does the *distribution* of latencies look like," which is what
a dashboard's latency chart is actually supposed to show. Both problems were
fixed together: `RecordLatency` is now called from
`internal/network/handler.go`'s `Handle` via a `defer` wrapped around the
whole command dispatch (so it measures every command's real end-to-end
handling time without threading timing code through 20 separate handler
functions), and `latencyBucket` gained real fixed-boundary bucket counters
(`<1ms, 1-5ms, 5-10ms, 10-25ms, 25-50ms, 50-100ms, 100-250ms, >=250ms`) so
there's an actual histogram to report, aggregated globally for the
dashboard's simple chart and per-command for the richer Prometheus export.

**Why a `defer` around the whole dispatch, rather than timing inside each
handler function individually?**
Because `Handle`'s dispatch is a single `switch` with ~20 cases, each calling
a different `handleX` function and `return`-ing its result directly — a
`defer` set up once, right after the metrics-collector nil-check, runs *no
matter which case fired or which specific `return` executed*, because Go
guarantees deferred functions run on every path out of a function, including
early returns. That's strictly less code and structurally impossible to
forget to add to a 21st handler added later — a real "let the language
guarantee correctness instead of hoping every future author remembers a
convention" decision.

**The Prometheus exporter — real vs. fake.** `internal/metrics/exporter.go`
emits standard Prometheus text format: `# HELP`/`# TYPE` header comments
followed by the actual metric lines. For the latency histogram
specifically, it emits a **genuine cumulative histogram** — `_bucket{le=
"0.005"}` lines where each successive `le` (less-than-or-equal) bucket's
count *includes* all lower buckets' counts (the actual Prometheus histogram
convention, which is what lets PromQL's `histogram_quantile()` function
compute percentiles from it correctly), plus `_sum` and `_count` lines, per
command (a `method` label) — not just a `# TYPE ... histogram` header with
no real series behind it, which would technically produce parseable output
while being useless for any real percentile query.

**JSON snapshot (`/api/stats`).** Rather than maintaining the histogram data
in two independently-hand-built places (a risk of the two silently drifting
apart over time), `cmd/server/main.go`'s `/api/stats` handler calls
`collector.LatencyHistogram()` — the exact same aggregation the Prometheus
exporter itself calls — and marshals it directly into the JSON response.

**Concurrency.** Every counter is an `atomic.Int64`/`atomic.Int32` — no
mutex needed for simple increment/read. The per-method latency buckets live
in a `sync.Map` (a map type specifically optimized for the "read-mostly,
occasional new key" access pattern — appropriate here since the set of
distinct command names is small and stable, but every single request reads
from it).

### Q&A: Metrics & Observability

**Q: Why `sync.Map` instead of a regular `map` with a mutex for the
per-method latency buckets?**
A: `sync.Map` is specifically optimized for exactly this access pattern:
many concurrent reads/updates to a small, mostly-stable set of keys (here,
command names — `GET`, `SET`, etc., which don't change once the server's
been running a while), with new keys added rarely. A plain map with a
`Mutex` would serialize *every* metric update behind one lock, becoming a
real contention point under high request volume; `sync.Map` avoids that for
the common "key already exists, just update it" case.

**Q: How would you compute p99 latency from what's actually exported here?**
A: Not directly from the JSON `/api/stats` histogram (it only gives raw
bucket counts, not a computed percentile) — you'd query Prometheus with
`histogram_quantile(0.99, rate(hydracache_request_duration_seconds_bucket
[5m]))`, which is exactly the standard PromQL pattern for percentiles from a
cumulative histogram, and is *why* the Prometheus exporter needed to be a
real cumulative histogram and not just gauges — gauges can't feed
`histogram_quantile` at all.

**Q: What's a real limitation of the fixed 8-bucket histogram boundaries
chosen here?**
A: They're fixed at author-time (`LatencyHistogramBounds`, hardcoded
`<1ms...>250ms`) rather than configurable — fine for this project's actual
observed latency range (an in-memory cache should mostly be sub-millisecond
to low-double-digit-milliseconds), but a workload with a very different
latency profile (say, mostly multi-second operations) would find every
sample landing in the single ">250ms" overflow bucket, making the histogram
useless for that workload. A more general system would expose bucket
boundaries as configuration.

## 4.12 Command-Line Client

**What.** `cmd/cli` (binary name `hc`) — a small, direct TCP/RESP client for
interacting with a HydraCache server from a terminal, analogous to
`redis-cli`.

**Why build a custom CLI instead of just telling everyone to use
`redis-cli`?** Two real reasons: first, proving the RESP implementation
actually round-trips correctly with an independently-written client (not
just the server's own internal test client) is itself a compatibility
signal; second, a project-specific CLI can add commands specific to this
project's own concepts (like `cluster info`/`cluster myid`) without needing
those to be indistinguishable from real Redis Cluster semantics, which
matters given the project's deliberate choice *not* to implement the actual
Redis Cluster wire protocol (see 4.4's Q&A and Part 7).

**A concrete, small, honest example from this session's own audit:** the
CLI's `cluster` command used to print a help line advertising "Cluster
subcommands: info, nodes, slots" — but the server had genuinely never
implemented `CLUSTER NODES` or `CLUSTER SLOTS` (they fell through to a bare
"unknown command" error, despite the *command name itself*, `CLUSTER`, being
registered in the server's own arity-validation table as a recognized
command — meaning the server's own bookkeeping said "I know this command,"
while its actual dispatch logic didn't implement it at all, a real internal
inconsistency). Once `CLUSTER INFO`/`CLUSTER MYID` were properly implemented
(honestly, with `CLUSTER NODES`/`SLOTS` explicitly refused with an
explanation rather than faked — see 4.4), the CLI's own help text was
corrected to advertise only what actually exists: "Cluster subcommands:
info, myid." A small fix, but a good illustration of "the CLI's own
documentation had drifted from the server's real behavior, and fixing it
required checking both sides, not just one."

### Q&A: CLI

**Q: If you were extending the CLI, what would you add first?**
A: Given the project's own documented gaps (Part 7), I'd add explicit,
helpful client-side error messages for command families the server doesn't
support at all (pub/sub, transactions) rather than letting the user hit a
bare protocol-level "unknown command" with no context — matching the same
honesty-first philosophy the rest of the project follows.

## 4.13 React Dashboard

**What.** `dashboard/` — a React + TypeScript + Tailwind + Recharts
single-page app that polls the server's JSON HTTP API (`/api/cluster`,
`/api/stats`) and renders cluster topology, replication lag, and metrics
charts in real time.

**The architecture:** two custom hooks, `useClusterData` and `useStats`
(`dashboard/src/hooks/`), each doing the same shape of thing — `fetch` on an
interval (`setInterval`, 2–3 seconds), track a `connected` boolean, and use a
`mountedRef` guard so a fetch that resolves *after* the component has
unmounted doesn't call `setState` on a dead component (a classic React
memory-leak/warning source if omitted). `App.tsx` combines both hooks'
`connected` flags and renders a persistent amber "Demo Data — Disconnected
from HydraCache backend" banner whenever either is false.

**The demo-data fallback — an honest design, worth explaining precisely.**
When a fetch fails, both hooks fall back to a hardcoded, plausible-looking
dataset instead of leaving the UI blank — but *only* while the disconnected
banner is simultaneously visible, so a viewer is never shown fabricated data
without an equally prominent label saying so. This is a deliberate design
choice for a demo/dev experience (letting someone open the dashboard and see
what it *looks like* without a live backend running), not an accident — the
key property that makes it honest rather than misleading is that the label
and the fallback data always appear together, never one without the other.

**What this session's audit found and fixed — the more important story
here, because it's about a place this honesty principle was being
*violated*, not followed.** Several dashboard elements displayed fabricated
data **unconditionally**, with no "demo data" label at all, regardless of
whether the backend was actually connected:
- A "Latency Distribution" chart (`LatencyHistogram.tsx`) that was
  **permanently hardcoded**, static numbers that never changed no matter what
  real traffic the server saw — indistinguishable at a glance from a real,
  live chart. Fixed by wiring it to the new, real backend histogram (4.11)
  when connected, with the *same* old hardcoded numbers preserved as the
  properly-labeled demo fallback rather than thrown away.
- A per-node "CPU %" bar and "Memory MB" figure in `NodeCard.tsx` and the
  node tables, backed by JSON fields (`load`, `memory_mb`) that — this is
  the deeper finding — were **never actually populated by any code path in
  the entire backend**, for *any* node, ever, even in a fully healthy,
  fully connected real cluster. They existed in the `cluster.Node` Go
  struct, were faithfully JSON-marshaled and unmarshaled, and the gossip
  wire format that's supposed to propagate node state between peers didn't
  even carry these fields in the first place — meaning even fixing "the
  local node's own load" wouldn't have made *other* nodes' cards show real
  numbers, because there was no transport for that data between nodes at
  all. This wasn't a UI bug, in other words — it traced all the way back to
  a real backend design gap (see 4.11 and Part 7). The honest fix, given
  that gap couldn't be closed in scope, was to **remove** the fields
  entirely (from the Go struct, the JSON API, and the dashboard) rather
  than leave a plausible-looking "0%"/"0 MB" sitting in the UI forever, and
  replace the display with something the backend genuinely does track: a
  "last seen Xs ago" indicator, computed from the real, gossip-populated
  `last_seen` timestamp.
- A "Cluster Logs" panel (`ClusterLogs.tsx`) that generates a continuous
  stream of entirely invented log lines client-side — including
  alarming-sounding ones like "Split-brain detection triggered on node-3" —
  with **no backend log-streaming API behind it at all** (HydraCache has no
  such API to build this on top of; building one was out of scope for this
  pass). Since removing a feature the user might specifically want to see
  isn't the same situation as removing a fabricated number, the fix here
  was to keep it but add a clearly visible "Simulated" badge, so it's never
  mistaken for a real operational log feed.

**Why is this such a good interview story, beyond "I fixed some bugs"?** It
demonstrates something most candidates don't proactively bring up:
*auditing your own UI's honesty*, not just its correctness. A dashboard that
compiles, has no console errors, and looks polished can still be actively
lying to whoever's looking at it if a chart or a stat never reflects real
system state — that's a subtler, more dangerous class of bug than a crash,
because nothing *tells* you it's wrong; it just quietly misleads. The fact
that this was caught by asking "what does this component's data actually
come from, all the way back to its source" for every single component,
rather than trusting that a component's *existence* implied its data was
real, is the actual transferable skill here.

### Q&A: React Dashboard

**Q: Why a `mountedRef` guard instead of, say, `AbortController` for the
fetch?**
A: Either would prevent the specific problem (setting state after unmount),
but `AbortController` additionally cancels the in-flight network request
itself, which is a genuine improvement this project doesn't currently make
— a fair "here's a concrete thing I'd improve" answer if pressed on it.

**Q: Concretely, how do you decide whether a piece of displayed data counts
as "fabricated" versus a legitimate simplification?**
A: The test I actually used: trace the value back to its source. If it
terminates at a real measurement (a counter incremented on a real code path,
a timestamp set by a real event) — even if the *visualization* of it is
stylized or simplified (like the ring diagram's client-side hash function
being a simpler stand-in for the real server-side one, still built from
real node IDs and count) — that's a legitimate simplification. If it
terminates at a hardcoded literal with no live data behind it *and* that's
not visibly labeled as such, that's fabrication, regardless of how
plausible the number looks.

**Q: What would break, right now, if a node's `last_seen` field were also
just a client-side illusion instead of real?**
A: Nothing would visibly break in the UI — it would just be as dishonest as
the fields that got removed. The reason it wasn't removed alongside them is
specifically that `last_seen` *is* genuinely populated by real gossip
activity server-side and actually reaches the JSON API — it passed the exact
trace-to-source test above, which is why it was chosen as the *replacement*
for the removed fake fields rather than being removed itself.

## 4.14 Reference Application (Read-Through Cache over Postgres)

**What.** `examples/readthrough/` — a small, real product-catalog HTTP API
demonstrating the classic **cache-aside** (a.k.a. read-through) pattern:
HydraCache in front of a real Postgres database, plus a live "kill a node"
control for demonstrating graceful degradation.

**Why does this exist as a separate Go module, not just another package in
the main project?** Because it needs its own dependencies — a Postgres
driver (`pgx`), the `go-redis` client library — that the *core cache engine*
has no business depending on. Giving it its own `go.mod` means
`internal/cache`, `internal/hashring`, etc. never pull in a SQL driver
transitively just because a demo app elsewhere in the repo happens to use
one — a real, deliberate module-boundary decision, not accidental structure.

**The cache-aside pattern itself, precisely:**
- **Read (`Service.GetProduct`):** check the cache first. On a hit, return
  it, done — the database is never touched. On a miss (or, critically, on a
  **cache error** — the cache being unreachable is deliberately treated the
  *same* as a clean miss, not as a request failure), fall through to the
  database, and on success, populate the cache for next time (best-effort —
  a failure to *write* the cache doesn't fail the read that already
  succeeded from the database).
- **Write (`Service.UpdateProduct`):** write to the database first (the
  system of record), then **invalidate** (delete) the cache entry — not
  update it in place. Why invalidate rather than update the cache directly
  with the new value? Because invalidate-then-let-the-next-read-repopulate
  is simpler and has no correctness gap as long as invalidation happens
  *after* the database write commits (which it does here, since
  `UpdateProduct` only invalidates after the store confirms the write) —
  whereas updating the cache directly requires you to correctly handle every
  possible interleaving with a concurrent read or write to avoid a stale
  value winning a race.

**"The cache is allowed to fail without taking the app down with it" — this
is the single most important sentence to be able to say clearly about this
subsystem, and it's *architecturally enforced*, not just an aspiration:**
`GetProduct`'s code checks the cache, and *any* error from it (a network
error, HydraCache being down entirely, a malformed cached value) falls
through to the database rather than propagating as a failed request. This
is directly, concretely demonstrated by the "kill a node" control: killing
the specific HydraCache node this demo is connected to doesn't break the
app — it just makes every subsequent read hit Postgres directly (slower,
correctly, and visibly reported as `"source": "database"` in the API
response) until the node comes back.

**An honestly-documented limitation of the demo itself, worth naming
proactively:** the demo's cache client connects to **one** fixed HydraCache
node address — the same simplification `cmd/cli` makes (4.12) — it does not
implement client-side routing across the cluster or automatic failover to a
different node. Killing the *specific* node it's connected to demonstrates
the graceful-degradation story above; killing a *different* node in the
cluster instead demonstrates HydraCache's own self-healing (which the
dashboard, not this demo app, is the right tool to observe).

**The "live kill-a-node" control — a real safety-conscious design worth
mentioning:** it's implemented by literally shelling out to `docker stop`/
`docker start` against named containers (`chaos.go`) — reusing the *exact
same two commands* `internal/chaostest`'s harness (4.15) already runs
against the same container-naming convention, not new, unproven, ad-hoc
shell-out logic. It's gated behind an explicit `-enable-chaos-controls` flag
that **defaults to false**, and when disabled, the corresponding HTTP
endpoints return `403 Forbidden` with an explanation — a deliberate,
documented decision *not* to containerize this specific app (see the
reference app's own README for the reasoning): running it on the host,
where the `docker` CLI and socket are already naturally available, avoids
having to mount the Docker socket into a container, which is a real,
well-known privilege-escalation surface not worth normalizing for a demo.

**Testing philosophy here — worth calling out directly, since it mirrors
this whole project's approach:** the cache-aside *logic* itself
(`service_test.go`) is tested against a **fake** `Store` and a **fake**
in-memory implementation of the exact three `go-redis` methods the code
actually calls (`Get`/`Set`/`Del`) — meaning the read-through/invalidate-on-
write logic is fully, deterministically unit-tested with **no live Postgres
or HydraCache cluster required to run the tests at all**. The HTTP layer
(`handlers_test.go`) is separately tested via Go's `httptest` package,
hitting real HTTP handlers with real request/response objects, still with no
live infrastructure. What's *not* covered by an automated test — and this is
stated explicitly in the reference app's own README rather than glossed
over — is the real Postgres wiring itself (`PostgresStore`) and the
docker-compose deployment path, because this development environment had no
working Docker daemon available to exercise them live.

### Q&A: Reference Application

**Q: Why is there an artificial delay (`-simulate-db-latency`, default 80ms)
added to every database query?**
A: Because a local demo Postgres instance on the same machine has near-zero
real network latency — nothing close to what a production database actually
experiences over a real network with real query complexity. Without some
stand-in for that, the entire point of the demo (showing that the cache
meaningfully speeds things up) would be invisible: cache hit and cache miss
would feel equally fast. This is explicitly documented as a labeled stand-in
for realistic latency, not a claim about Postgres's actual performance —
an important distinction to volunteer if asked, since silently faking
"realistic" numbers without saying so would be exactly the kind of
dishonesty the rest of this project works hard to avoid.

**Q: What would you need to change to make this demo route correctly across
a real multi-node cluster instead of one fixed node?**
A: Either implement genuine Redis Cluster protocol support in HydraCache
itself (MOVED/ASK redirects, so any client library that already understands
that protocol works unmodified — see Part 7), or write a custom client-side
router in the demo that hashes each key the *same way* HydraCache's own ring
does and connects to whichever node that computes as the owner — which is
close to what `internal/chaostest`'s own ring mirror already does (4.4), just
not currently reused for live request routing in this demo app.

**Q: This uses `go-redis` — how do you know that actually proves real
compatibility, rather than just "the demo happens to work"?**
A: Because `go-redis` is a fully independent, widely-used, real-world Redis
client library — not code either the demo or the core server wrote — and
`internal/network/goredis_compat_test.go` in the main module separately
drives an actual HydraCache server with this exact same library across
PING, SET/GET (including NX/XX/EX flags), SETNX, DEL, EXISTS, EXPIRE, error
handling, and the default-RESP3-negotiation-falls-back-to-RESP2 path. That
compatibility suite is what caught a real gap during this session — `SETNX`
(the classic two-argument form) wasn't implemented at all, because
`go-redis`'s `SetNX` method sends that exact command on the wire, not `SET
key value NX` — and it got fixed as a direct result of testing against a
real client instead of only ever testing against code I wrote myself.

## 4.15 Chaos Testing Harness

**What.** `internal/chaostest` and `cmd/chaos` — an end-to-end, Docker
Compose-driven test harness that runs real chaos scenarios (kill the
primary, rolling restart, add a node and verify migration, partition and
heal, chaos under concurrent load) against a real 5-node cluster and reports
pass/fail per scenario.

**Why does this matter as a category of testing, distinct from unit tests?**
Because unit tests (like everything in Part 4's other sections) verify one
function or one package's logic in isolation, with fakes standing in for
everything else. Chaos testing verifies the *emergent, cross-node behavior*
that only exists when real processes, real network connections, and real
timing are all involved simultaneously — you cannot unit-test "does the
cluster actually promote a new leader and keep serving correct data within
30 seconds of the real primary process being killed," because that
statement is fundamentally about the interaction of multiple real running
processes over real time, not about any single function's return value.

**The five scenarios, and what each one actually proves:**
1. **Kill Primary → Verify Promotion.** Write a key to its real hash-ring
   primary, confirm (by polling, not assuming) that all 5 nodes actually
   have the replicated data, then kill that primary process, and verify: a
   new leader gets elected, and — this is the important, non-obvious check
   — the key is specifically readable *from the newly-promoted leader*,
   with the correct value. Why insist on reading from the *new leader*
   specifically, rather than just "any surviving node"? Because a replica
   surviving with stale-but-present data proves nothing about whether
   failover actually *works* — the real question is whether the node that's
   now authoritative actually has the data.
2. **Rolling Restart.** Write 100 keys, then restart every node one at a
   time (waiting for full cluster health between each), verifying all 100
   keys are still correctly readable (from *any* node, since replication may
   have placed different keys on different nodes) after every single
   restart — proving the cluster tolerates a standard rolling-deploy
   pattern without data loss.
3. **Node Join → Triggers Real Migration.** Write keys to a healthy 5-node
   cluster, record which node the *real* hash ring (mirrored independently
   in `internal/chaostest/ring.go`, using the identical FNV-1a algorithm and
   150-vnode count as the production ring — see 4.4) says should own each
   key, add a genuinely brand-new 6th node that was never previously part of
   the cluster, and verify: the keys that the ring math says *should* have
   moved to the new node actually did move (present on the new node,
   *absent* from their old owner), with an explicit cross-check for the
   worst possible outcome — a key removed from its old owner but *not*
   present on the new node, which the test explicitly flags as `"DATA
   LOSS"` if it ever occurs.
4. **Partition and Heal.** Disconnect one node from the Docker network
   entirely (a real, not simulated, network partition), verify the
   surviving majority doesn't fully fracture (at least one side elects a
   leader — split-brain during an active partition is explicitly
   *expected* and tolerated here, since a minority can't reach quorum
   anyway, per 4.7's election design), then reconnect the node and verify
   full gossip reconvergence — bounded by a deliberately generous 90-second
   timeout, because partition-heal reconvergence genuinely takes longer
   than normal gossip rounds (see 4.8's explanation of why).
5. **Concurrent Chaos.** Run continuous background read/write load in a
   goroutine while simultaneously killing a node and verifying failover
   *during* that live load, then check that the background load's overall
   error rate stayed under an acceptable threshold (20%) rather than
   requiring zero errors — an honest acknowledgment that some transient
   errors *during* an active failover are expected and fine; the property
   worth actually asserting is that the system recovers and errors don't
   spiral or persist.

**Every wait in this harness polls real state with a bounded timeout — it
never uses a fixed `sleep()` to "probably" have waited long enough.** The
shared `WaitFor(description, timeout, interval, condition)` helper polls a
condition function on an interval until it's true or the timeout elapses,
returning a descriptive error including the *last observed state* on
failure (not just "timed out") — because a fixed sleep is both slower than
necessary in the common case (you always wait the full fixed duration even
if the condition was true almost immediately) and less reliable in the
uncommon case (if the real system is just a bit slower than whatever
fixed duration you guessed, the test fails even though the system would have
correctly converged one second later).

**This session's own audit of this harness, before committing it.** The
harness code had been written and was already building cleanly, but it had
been sitting **untracked** in the working directory the entire time — meaning
it was completely invisible to the CI pipeline's linter and had never
actually been reviewed. Committing it properly (rather than blindly) meant
first auditing it the same way everything else in this project got audited:
that review found and removed several genuinely dead pieces (a generic
`Shuffle[T]` helper, two hash-ring methods, two harness methods, a client
method pair) that were defined but called from nowhere in the entire
codebase, and fixed real lint findings — an unchecked error return, several
`govet shadow` bugs — that the project's CI-pinned linter caught the moment
the package actually became visible to it.

**An honest, explicitly-stated limitation of this section of the project:**
this harness requires a real Docker daemon and a real 5-node
`docker-compose` cluster to actually *run* — it could not be executed live in
this particular development environment (no working Docker daemon was
available), so while the code is real, reviewed, and lint-clean, whether its
five scenarios currently *pass* against a live cluster is honestly
unverified as of this document, and is explicitly documented as such rather
than assumed.

### Q&A: Chaos Testing Harness

**Q: What's the single most important design property of a good chaos test,
based on how this one is built?**
A: That every assertion checks *real, observed state* via polling, not
elapsed wall-clock time or an assumption about internal implementation
timing. A chaos test that uses `time.Sleep(10 * time.Second)` and then
checks state once is really asserting "the system probably converged within
10 seconds," which is both slower than necessary and silently wrong the
moment real timing shifts even slightly — versus polling with `WaitFor`,
which is both faster in the common case and correctly patient in the slow
case, and fails with a precise, actionable "here's what I actually observed
when I gave up" message rather than a bare timeout.

**Q: Why does the "Node Join" scenario build an independent hash-ring
implementation in the test harness instead of importing the real
`internal/hashring` package directly?**
A: Because the chaos harness runs against nodes as *external black boxes*
over the network (Docker containers, reached via TCP) — it deliberately
doesn't link against the server's internal Go packages at all, the same way
a real external client never could. Reimplementing the identical ring
algorithm (same FNV-1a hash, same 150 virtual nodes) as an independent
verification tool means the test is actually checking "does the real
system's behavior match what the algorithm *should* produce," rather than
being structurally unable to disagree with the implementation it's
supposed to be verifying (which would be the failure mode of importing the
real package directly and calling its own function to check its own
answer).

**Q: If asked "did you actually run this and see it pass" — how do you
answer honestly?**
A: Exactly as stated above: the code builds, passes the linter, and was
reviewed line-by-line for dead code and correctness — but this specific
environment had no working Docker daemon, so live execution against a real
cluster is honestly unverified, and that's stated plainly rather than
implied otherwise. This is a good moment to point out that saying this
plainly, instead of hoping the interviewer doesn't ask, is itself
consistent with how the whole project is documented (see Part 7) — an
interviewer who's paying attention will notice that consistency
positively.

# Part 5: Concurrency & Correctness

This project touches nearly every common Go concurrency primitive, and —
importantly — found and fixed **real** races and correctness bugs along the
way, not hypothetical ones. Being able to talk through a couple of these in
concrete detail is worth more than reciting definitions.

**The primitives used, and why each one specifically:**
- **`sync.Mutex`**: the cache store (4.3) — every access needs to mutate
  ordering/frequency bookkeeping, so a plain mutex (not RWMutex) is the
  honest choice.
- **`sync.RWMutex`**: the hash ring (4.4) and the phi-accrual detector's
  entry map (4.6) — reads (lookups) vastly outnumber writes (membership
  changes), so letting reads proceed concurrently is a real win.
- **`atomic.Int64`/`atomic.Int32`/`atomic.Bool`/`atomic.Uint64`**: simple
  counters and flags where a full mutex would be needless overhead — metrics
  counters (4.11), connection IDs (4.2), election's `electing`/
  `heartbeating` guards (4.7), gossip's incarnation number (4.8).
- **`sync.Map`**: per-method latency buckets (4.11) — the specific
  read-heavy, stable-key-set access pattern it's designed for.
- **`atomic.Pointer[T]`**: the process-wide swappable outbound TLS config
  (4.2) — lets every dialer read the current config without a lock, and lets
  it be atomically swapped wholesale.
- **Goroutines with a `context.Context` for cancellation**, and a
  `sync.WaitGroup` to know when they've actually finished — used throughout
  for background loops (active expiration sweeps, gossip rounds, election
  timers, the periodic metrics-refresh loop) so shutdown can *wait* for
  them to actually stop, not just signal them and hope.

**Real races/bugs found this session (have 2–3 of these ready in detail,
not just the list):**
1. **LFU's non-deterministic tie-break** (4.3) — not a data race in the Go
   race-detector sense (no unsynchronized concurrent access), but a
   *correctness* race in the broader sense: unpredictable behavior driven by
   Go's intentionally-randomized map iteration order.
2. **The negative-bulk-length parser crash** (4.1) — a crash reachable by
   any unauthenticated connection, found while implementing connection
   limits, not originally reported.
3. **`MaxConns` not actually enforced before `Accept()`** (4.2) — the
   semaphore existed, but its placement made it not actually bound resource
   consumption the way its name promised.
4. **Several `govet shadow` bugs**, caught by the CI-pinned linter — an
   inner `:=` accidentally re-declaring an outer variable of the same name
   (typically `err`) instead of reusing it, meaning an error from the inner
   scope silently never propagated to where the outer code checked it. A
   good concrete example: in the go-redis compatibility test's `SetXX`
   subtest, `if err := client.Set(...); err != nil` inside a block where an
   outer `err` from an earlier `SetXX` call was still in scope shadowed
   that outer variable — harmless in that *specific* test's logic, but
   exactly the kind of bug that, in production code instead of test code,
   would mean "an error happened, and the code that should have checked it
   checked the wrong variable and saw `nil`."
5. **A stale local lint cache producing a false-clean result** — this isn't
   a bug in the *project's* code, but a real, worth-mentioning process
   finding: running `golangci-lint` locally reported zero issues, while the
   exact same commit's CI run correctly failed on a real `govet shadow`
   finding — because the local tool's own incremental cache had gone stale
   and was returning a cached "clean" result for a file whose content had
   since changed. The fix wasn't just fixing that one shadow bug — it was
   changing the *process*: every subsequent lint check that session used an
   explicitly fresh, uniquely-named cache directory
   (`GOLANGCI_LINT_CACHE=<fresh dir>`) so a stale cache could never again
   produce a false-clean result. This is a genuinely good story about
   distinguishing "my code is buggy" from "my *verification process* has a
   bug," and fixing the latter so the former can't recur silently.

**How every concurrency-sensitive change in this project was actually
verified — this is a process point worth stating explicitly if asked "how
do you know your concurrent code is correct":**
1. `go build ./...` and `go vet ./...` — compiles, and passes Go's own
   static analysis (which includes real bug classes like the shadow
   detector, wrong `Printf` verbs, and more).
2. `go test -race ./...` — every test run under Go's race detector, which
   instruments memory accesses at runtime and reports genuine
   read/write or write/write races with byte-accurate detail (not just
   "probably a race" — one specific example is enough to have a stack trace
   for). A change is never considered done until this is clean.
3. `go test -race -count=10 <touched packages>` — running the *same* tests
   ten times in a row specifically to shake out flakiness driven by
   goroutine scheduling order, which varies between runs even without any
   code change — a bug that only manifests with unlucky scheduling might
   pass once and fail on the third or seventh run.
4. `gofmt -s` for formatting, and the project's exact CI-pinned
   `golangci-lint` configuration (not just "some linter, some version") run
   locally before every push, specifically to catch the class of "passes
   locally, fails in CI" problem this session hit twice — once from a Go
   toolchain version mismatch (local ambient Go was incompatible with the
   pinned linter's own bundled type-checker, causing it to silently produce
   false-clean results — fixed by installing the exact CI-pinned Go version
   side-by-side and always using it for verification) and once from the
   stale-cache issue above.

**Q: Why prefer atomics over a mutex wherever possible, rather than just
using a mutex everywhere for consistency?**
A: A mutex around even a single integer increment is meaningfully more
expensive than an atomic operation, at the volume of a per-request counter
increment — this genuinely matters when it's in the hot path of every
single command dispatched (like `IncrRequests`). But it's not a universal
rule: atomics only compose safely for a *single* variable's operations: the
moment you need to keep two related pieces of state consistent with each
other (e.g., the LRU's map and its linked list must always agree), a mutex
protecting *both together* is the correct and necessary tool — that's
exactly why `internal/cache/store.go` uses a plain mutex even though it
also happens to use one `atomic.Int64` (`memBytes`) *alongside* it: the
atomic is for one genuinely independent piece of state, not a substitute
for the mutex protecting everything that must stay mutually consistent.

# Part 6: Design Decisions and Trade-offs

Frame every answer here as: *here's the alternative I considered, here's why
I didn't pick it, here's the cost I accepted in exchange.* That structure is
what separates "I made a choice" from "I made a *reasoned* choice."

**Q: Why Go?**
A: Goroutines and channels make the concurrency this project is fundamentally
about (many simultaneous connections, background gossip/heartbeat/election
loops, replication fan-out) dramatically less error-prone to write than
thread-and-lock-based concurrency in a language without lightweight
concurrency primitives built in. Static typing plus a genuinely fast
compiler keeps iteration quick despite the type safety. And Go's standard
library already has production-quality `net`, `crypto/tls`, and `context`
packages, meaning the actual distributed-systems logic — not
socket-handling boilerplate — is where the real work and the real learning
happened.

**Q: Why not use an existing Raft library (e.g., hashicorp/raft) or gossip
library (e.g., hashicorp/memberlist)?**
A: The explicit goal (see Part 2) was building the actual primitives myself,
specifically so every mechanism is one I can personally explain end to end,
including its edge cases and failure modes — using a mature existing library
would have given a more battle-tested result for a production system, but
would have taught me (and would let me demonstrate) far less about *why*
these mechanisms work the way they do. In an actual production system I was
being paid to build reliably and quickly, I would absolutely lean on a
proven library like `hashicorp/raft` rather than re-deriving Raft myself —
this project's choice not to is specifically because its purpose is
learning and demonstrating understanding, not shipping the fastest possible
reliable system.

**Q: Why RESP2 instead of implementing full RESP3 support?** (See also 4.1's
Q&A for the protocol-level detail.)
A: Partial protocol support that silently breaks in ways a client doesn't
expect is worse than complete, honest support for an older-but-still-
totally-functional version. RESP3's actual new capabilities (real booleans,
doubles, a distinct null type, maps/sets as first-class wire types) aren't
things this project's command set currently needs anyway — nothing here
returns a boolean or a double over the wire — so the practical cost of not
implementing RESP3 fully is close to zero, while the cost of implementing it
*badly* (accepting the negotiation, then replying with RESP2-shaped data the
client now expects to be RESP3-shaped) would be a genuine compatibility trap.

**Q: Why consistent hashing with virtual nodes instead of, say, a fixed
16384-slot model like real Redis Cluster?**
A: Both solve the same underlying problem (bounded reshuffling on membership
change); Redis Cluster's fixed-slot model (CRC16(key) mod 16384, then slots
assigned to nodes) is simpler to reason about and lets a client precompute
routing without needing to know virtual-node positions, but requires an
explicit slot-migration protocol and administrative slot-assignment step
when nodes change. A pure consistent-hash ring is simpler to implement from
scratch (which mattered for this project's goals) and rebalances more
"automatically," at the cost of the resulting ownership boundaries being
less human-predictable than "slot 4000-8000 belongs to node B." This is
also *exactly* why this project deliberately does **not** claim to speak the
real Redis Cluster protocol (see 4.4 and Part 7) — a real Redis Cluster
client computing CRC16 slots and trying to route directly based on that math
would be silently wrong against this server's actual, different routing
algorithm; claiming Cluster-protocol compatibility without actually matching
its slot math would be a correctness bug, not just a documentation gap.

**Q: Why is the leader election's term completely separate from the
replication epoch, instead of one unified "generation" number for the whole
cluster?** (See also 4.5's and 4.7's Q&A.)
A: Because they answer genuinely different questions that can legitimately
change independently: "who is cluster coordinator" (an election concern)
versus "has this specific shard's ownership changed" (a per-shard topology
concern). A single, cluster-wide leader owning all data (where unifying
these would make sense) is a different architecture than sharding via
consistent hashing (what this project actually does) — conflating the two
concepts here would either be meaningless or actively wrong, not just
redundant.

**Q: What's the single design decision you'd most want to revisit if you
had more time?**
A: Making writes correctly route to (or be forwarded to) a key's actual
primary regardless of which node a client happens to connect to — right now
a write to a non-primary node succeeds locally but silently isn't
replicated anywhere (Part 7's most significant honestly-documented gap).
Closing that requires either real Cluster-protocol MOVED/ASK redirects, or
a server-side write-forwarding layer, and I'd rather say precisely that than
either overstate what's solved or pretend the gap is smaller than it is.

# Part 7: What Is NOT Implemented (and why that's a strength)

**Say this explicitly if it comes up, in almost these words:** *"I did a
full audit of my own claims and built `COMMANDS.md`, generated by reading
the actual dispatch code, listing exactly what's implemented, partial, or
missing — because I'd rather under-claim and be right than over-claim and
get caught."* Interviewers who work on real systems have all been burned by
someone else's over-claimed feature; demonstrating you already hold
yourself to that standard, unprompted, is one of the highest-leverage things
you can say in this entire interview.

**The honest, complete list (see `COMMANDS.md` and this document's Parts
4.1–4.15 for the detail behind each):**

1. **No real Redis Cluster wire protocol** (no CRC16 slot assignment, no
   `MOVED`/`ASK` redirects). Deliberate — see 4.4's and Part 6's reasoning.
2. **No RESP3.** Deliberate, and honestly refused (`NOPROTO`) rather than
   half-implemented. See 4.1.
3. **No pub/sub over the wire**, despite a real, tested, working in-process
   pub/sub broker (`internal/pubsub`) existing in the codebase — it was
   simply never wired to the client-facing protocol at all. This session's
   audit found it being constructed and immediately discarded
   (`broker := pubsub.NewBroker(); _ = broker`) in `main.go` and removed that
   dead construction, documenting the gap honestly in `COMMANDS.md` instead
   of leaving a misleading half-connection in place.
4. **No transactions** (`MULTI`/`EXEC`/`DISCARD`/`WATCH`), no Lua scripting,
   no secondary data types (only string values — no hashes, lists, sets,
   sorted sets).
5. **Writes to a non-primary node aren't replicated** — the single most
   significant gap, discussed in depth in 4.5, 4.14, and Part 6.
6. **The `REPLICA_SYNC` pull path exists but is unreachable** — implemented
   correctly on the primary side, with zero callers anywhere, documented
   directly in the code as a known scope boundary rather than silently
   dead. See 4.5.
7. **No mutual-TLS peer-identity verification** — TLS/mTLS infrastructure
   exists and works, but a connecting peer's *specific* certificate identity
   isn't checked against an expected peer list yet. See 4.10's Q&A.
8. **The metrics/admin HTTP endpoints have no authentication at all.**
   See 4.10's Q&A — a real, current limitation, not a design decision to
   defend.
9. **Per-node CPU/memory in cluster state was removed, not fixed** — those
   fields existed in the JSON API and Go structs but were never populated by
   any code path, and the gossip wire format never even carried them between
   nodes. Rather than leave misleading always-zero fields (or the dashboard
   displaying them as if real), this session removed them entirely. See
   4.13.
10. **The chaos-testing harness's scenarios are unverified in this specific
    development environment**, due to no available Docker daemon — the code
    is real, reviewed, and lint-clean, but "does it currently pass against a
    live cluster" is explicitly stated as unknown rather than assumed. See
    4.15.

**If an interviewer asks "why should I trust a system with this many gaps?"**
— reframe it directly: *every one of these is written down, in this exact
document and in the project's own `COMMANDS.md`, specifically because I
audited for them myself rather than waiting to be asked.* A system with
zero documented gaps either has none (extremely unlikely for any real
system) or has an author who hasn't looked hard enough — and this project's
actual differentiator is the audit process itself, which found and fixed
real bugs (the parser crash, the connection-limit bug, the LFU tie-break,
the dead `RecordLatency`, the dashboard's fabricated data) specifically
*because* it was looking for exactly this kind of gap, not because those
bugs were reported by someone else.

# Part 8: System Design Interview Questions

These are broader "design a system" questions an interviewer might ask,
using this project as your concrete grounding. For each, a short model
answer *rooted in what you actually built*, not generic system-design
trivia.

**Q: Design a distributed cache.**
A: Walk through Part 3's diagram top to bottom: client → protocol parsing →
auth → command dispatch → in-memory store (with an eviction policy and TTL)
→ durability (WAL before mutation) → sharding (consistent hashing with
virtual nodes, to bound reshuffling on membership change) → replication
(per-shard, async by default with an optional sync mode) → failure detection
(phi-accrual, not a fixed timeout, because real networks have variable
jitter) → cluster coordination (gossip for membership dissemination, a
lightweight election for a coordinator role, kept deliberately separate
from per-shard data ownership) → observability (metrics, both
pull-based JSON and Prometheus). Then proactively name the trade-offs you'd
make differently for different constraints — e.g., "if I needed the
sharding to be transparent to any generic Redis Cluster client, I'd
implement the real Cluster protocol instead of my own hash ring's routing;
if durability mattered more than raw throughput, I'd default to
`SyncAlways` instead of `SyncEverySec`."

**Q: How would you scale this to 100 nodes?**
A: The hash ring itself scales fine algorithmically (150 virtual nodes ×
100 physical nodes = 15,000 ring positions, still trivially fast to binary-
search) — the actual bottleneck at that scale would be gossip: pure
random-peer gossip's convergence time grows with cluster size (more hops
needed to reach everyone), so at 100 nodes I'd want to look at whether the
gossip fanout (how many random peers each round contacts) needs tuning, and
whether the election's `PeersFunc`-based quorum computation (which today
assumes a full membership list is cheap to obtain and iterate) still holds
up. I'd also want per-shard replication factor to matter more explicitly at
this scale — with 100 nodes, a replication factor of 2 means a huge fraction
of the cluster holds no copy of any given key at all, which is fine for
availability math but worth being deliberate about, not accidental.

**Q: How do you handle split-brain?**
A: Two distinct places this could occur, and the design's honest answer for
each: (1) During an active network partition, the *election* deliberately
tolerates a minority side electing nobody (since quorum is computed against
total known membership, not just reachable members — see 4.7) — this is
correct-but-unavailable-on-the-minority-side behavior, the standard CP
trade-off. (2) For the *data path* specifically, replication's epoch
fencing (4.5) means even if two nodes briefly both believed themselves
primary for a shard during a partition, the one operating on a stale epoch
gets its writes rejected by replicas once the epoch has actually advanced —
though I'd be honest that this doesn't retroactively fix writes that
happened locally on the stale side before that rejection kicks in, since
this project's replication doesn't implement full multi-version
conflict resolution.

**Q: Design a system to detect node failure in a cluster.**
A: This is directly 4.6 — explain phi-accrual precisely (the formula, why a
fixed timeout is wrong, the debouncing via `SuspectTimeout` on top of the
statistical model, the practical stddev floor) and be ready to compare it
explicitly against simpler alternatives (fixed timeout — too rigid; TCP
keepalive alone — doesn't distinguish "slow" from "dead," and doesn't
survive a process that's alive but hung).

**Q: How would you add rate limiting to this system?**
A: I'd add it at the same layer connection limits already live
(`internal/network/server.go`) — per-connection or per-user token buckets,
checked in `HandleAuthenticated` right alongside the existing ACL check,
since that's already the single choke point every client command passes
through before reaching the dispatch logic. I'd track "is this actually
needed" by first checking whether the existing `MaxConns` semaphore and
per-operation read/write timeouts (4.2) already cover the failure modes I'm
worried about, rather than assuming more limiting is automatically better.

# Part 9: Algorithm / Coding Questions Rooted in This Project

Practice actually writing these, not just reading the answer. Complexity is
noted for each.

**Q1: Implement an LRU cache with O(1) get and put.**
This is *exactly* `internal/cache/eviction.go`'s `LRU`. The shape:
```go
type LRU struct {
    capacity int
    items    map[string]*list.Element
    order    *list.List // front = most recently used, back = least
}

func (l *LRU) Get(key string) (*Entry, bool) {
    if el, ok := l.items[key]; ok {
        l.order.MoveToFront(el)
        return el.Value.(*lruEntry).value, true
    }
    return nil, false
}

func (l *LRU) Put(entry *Entry) {
    if el, ok := l.items[entry.Key]; ok {
        l.order.MoveToFront(el)
        el.Value.(*lruEntry).value = entry
        return
    }
    if l.order.Len() >= l.capacity {
        oldest := l.order.Back()
        l.order.Remove(oldest)
        delete(l.items, oldest.Value.(*lruEntry).key)
    }
    el := l.order.PushFront(&lruEntry{key: entry.Key, value: entry})
    l.items[entry.Key] = el
}
```
**Why O(1):** a doubly-linked list gives O(1) insert-at-front, O(1) removal
of any known node (given a pointer to it, which the map provides), and O(1)
removal of the back. The map gives O(1) lookup from key to that node
pointer. Neither structure alone would be O(1) for everything a real LRU
needs — a map alone has no ordering; a linked list alone needs O(n) to find
a given key's node without the map's help.

**Q2: Implement consistent hashing with virtual nodes.**
This is `internal/hashring/ring.go`. Key parts to be able to write cold:
```go
func (hr *HashRing) AddNode(nodeID string) {
    for i := 0; i < hr.virtualNodes; i++ {
        pos := hash(fmt.Sprintf("%s#%d", nodeID, i))
        hr.ring = append(hr.ring, pos)
        hr.nodes[pos] = nodeID
    }
    sort.Slice(hr.ring, func(i, j int) bool { return hr.ring[i] < hr.ring[j] })
}

func (hr *HashRing) GetNode(key string) string {
    if len(hr.ring) == 0 {
        return ""
    }
    h := hash(key)
    idx := sort.Search(len(hr.ring), func(i int) bool { return hr.ring[i] >= h })
    if idx == len(hr.ring) {
        idx = 0 // wrap around — the ring is circular
    }
    return hr.nodes[hr.ring[idx]]
}
```
**Complexity:** `GetNode` is O(log(N×V)) where N = nodes, V = virtual nodes
per node (binary search over the sorted ring). `AddNode`/`RemoveNode` are
O(N×V × log(N×V)) due to the re-sort. **Be ready to explain the "wrap
around" line** — it's the one detail people most often forget: if the key's
hash is greater than every position on the ring, ownership wraps back to
the very first position, because the ring is circular, not linear.

**Q3: Implement a phi-accrual failure detector's core scoring function.**
```go
func phi(elapsed, meanInterval, stddev float64) float64 {
    if stddev == 0 {
        stddev = 0.01 // avoid division by zero
    }
    y := (elapsed - meanInterval) / (stddev * math.Sqrt2)
    return -math.Log10(0.5 * math.Erfc(y))
}
```
Be ready to explain *why* this formula, not just recite it: it treats past
inter-arrival intervals as samples from a normal distribution, computes the
probability of still waiting this long if the peer were healthy
(`0.5 * erfc(...)` is exactly that tail probability), and converts a
shrinking probability into a growing suspicion score via `-log10`.

**Q4: Given a stream of (timestamp, node_id) heartbeat events, maintain a
rolling mean and variance of inter-arrival times per node, bounded to the
last N samples.** (This is `HeartbeatEntry.RecordInterval` /
`pruneLocked` / `stats`.)
```go
type Entry struct {
    lastSeen time.Time
    samples  []time.Duration
    window   int
}

func (e *Entry) Record(now time.Time) {
    if !e.lastSeen.IsZero() {
        e.samples = append(e.samples, now.Sub(e.lastSeen))
        if len(e.samples) > e.window {
            e.samples = e.samples[len(e.samples)-e.window:]
        }
    }
    e.lastSeen = now
}

func (e *Entry) MeanAndVariance() (mean, variance float64) {
    if len(e.samples) == 0 {
        return 0, 0
    }
    var sum float64
    for _, s := range e.samples {
        sum += float64(s)
    }
    mean = sum / float64(len(e.samples))
    for _, s := range e.samples {
        d := float64(s) - mean
        variance += d * d
    }
    variance /= float64(len(e.samples))
    return
}
```
The real implementation additionally prunes by *age*, not just count — be
ready to explain why both bounds matter (count alone doesn't handle a node
that suddenly goes quiet for a long time then resumes with a very different
timing profile; age alone doesn't bound memory usage under a very chatty
peer).

**Q5: Given a set of keys and a set of nodes, write a function that
computes which keys would move if a new node were added to a consistent-hash
ring (without actually mutating any real ring).**
This is exactly what `internal/chaostest/scenarios.go`'s Node Join scenario
does: build the ring twice (once with the old node set, once with the new
node set added), compute each key's owner under both, and diff. The key
insight for the "who moved" check specifically: a key only counts as
"should migrate" if its new owner is the added node *and* its old owner
was *not* the added node (guards against a trivial no-op if a key happened
to already resolve to that ID for some other reason).

**Q6: Design a rolling histogram with fixed bucket boundaries, updated
concurrently from many goroutines, that can report a snapshot cheaply.**
This is 4.11's `latencyBucket`:
```go
type Histogram struct {
    total   atomic.Int64
    count   atomic.Int64
    buckets [8]atomic.Int64
}

func (h *Histogram) Record(d time.Duration, bounds []int64) {
    ns := d.Nanoseconds()
    h.total.Add(ns)
    h.count.Add(1)
    idx := len(bounds) // overflow bucket
    for i, bound := range bounds {
        if ns < bound {
            idx = i
            break
        }
    }
    h.buckets[idx].Add(1)
}
```
Why atomics and a fixed-size array rather than a mutex-guarded slice: every
bucket increment is independent of every other bucket, so there's no
cross-field consistency requirement to protect with a single lock — each
`atomic.Int64` can be updated completely independently and concurrently,
which is both simpler and faster than mutex-guarding the whole struct for
what is, per-call, a single independent counter update.

# Part 12: Glossary

- **RESP** — REdis Serialization Protocol; the text-based wire format this
  project's TCP server speaks (version 2 only — see 4.1).
- **Consistent hashing** — a technique for mapping keys to nodes on a
  circular hash space such that adding/removing a node only reassigns a
  small, bounded fraction of keys (see 4.4).
- **Virtual node (vnode)** — one of several hash-ring positions a single
  physical node is given, to smooth out uneven key distribution and avoid
  hot-spotting a single neighbor on node removal (see 4.4).
- **Phi-accrual failure detection** — a statistical approach to liveness
  detection that scores suspicion based on how anomalous a heartbeat delay
  is relative to that peer's *own* historical timing, rather than a fixed
  timeout (see 4.6).
- **Gossip protocol / SWIM** — a membership-dissemination technique where
  nodes periodically exchange state with random peers, spreading
  information exponentially without needing direct all-to-all
  communication (see 4.8).
- **Incarnation number** — a self-controlled counter a node bumps to
  refute stale or false rumors about its own state spreading through
  gossip (see 4.8).
- **Raft** — a consensus algorithm for electing a leader and replicating a
  log with strong safety guarantees; this project implements a simplified
  subset (term persistence, pre-vote, quorum, lease) for a
  cluster-coordinator role, not for the data path itself (see 4.7).
- **Pre-vote** — an extra round before a real Raft election that lets a
  candidate check "would you vote for me" without incrementing its actual
  term, preventing a partitioned node from inflating its term while
  isolated (see 4.7).
- **Quorum** — a majority of the *total known* cluster membership (not just
  reachable members) required to elect a leader or confirm a
  sufficiently-replicated write (see 4.5, 4.7).
- **Topology epoch** — a monotonically increasing number tracking
  membership/ownership changes, used to fence stale replicated writes after
  a shard's ownership changes (see 4.5) — distinct from the election term.
- **WAL (Write-Ahead Log)** — an append-only durability log written before
  an in-memory mutation, so a crash can never lose an acknowledged write
  (see 4.9).
- **Cache-aside / read-through pattern** — a caching strategy where reads
  check the cache first and fall back to (and repopulate from) the system
  of record on a miss; writes go to the system of record and invalidate
  (rather than update) the cache entry (see 4.14).
- **LRU / LFU** — Least Recently Used / Least Frequently Used, two eviction
  policies for deciding which cached entry to remove under capacity
  pressure (see 4.3).
- **ACL (Access Control List)** — per-user permissions restricting which
  commands and which key patterns a given authenticated user may use
  (see 4.10).
- **mTLS (mutual TLS)** — TLS where both sides present and verify a
  certificate, not just the server (see 4.2, 4.10).
- **Split-brain** — a failure mode where a network partition causes more
  than one node to simultaneously believe it holds sole authority (leader
  status, or primary-for-a-shard status) over the same data (see 4.7's and
  Part 8's discussion of how this project's design tolerates it on the
  election side and partially mitigates it on the data side via epoch
  fencing).
- **Chaos testing** — deliberately injecting real failures (killing a
  process, partitioning a network) into a running system to verify its
  actual emergent behavior under failure, as opposed to unit-testing
  individual functions in isolation (see 4.15).
